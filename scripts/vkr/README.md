# Воспроизведение E2E и съёмки ВКР

## QA этапа 2: обновлённые экраны

Для съёмки через webpack задайте `VKR_DEV=true`, `VKR_PORT=3370`, `NEXT_DIST_DIR=.next-qa` и запустите `npx tsx scripts/vkr/server.ts`. Для записанного веб-резерва запустите второй процесс с `VKR_AI_DEMO=true`, `VKR_PORT=3371`, `NEXT_DIST_DIR=.next-qa-web`. Генератор: `VKR_BASE_URL=http://localhost:3370`, `VKR_WEB_BASE_URL=http://localhost:3371`, `npx tsx scripts/vkr/screenshots.ts`. `VKR_FROM_OFFER=true` продолжает съёмку с КП, сохраняя уже снятые кадры 01–09 из manifest. Пароли не передаются в аргументах команд.

Кадр `10c-offer-pdf-page1.png` — Poppler-рендер фактически скачанного через кнопку PDF (`pdftoppm` обязателен). `11b` показывает форму серии по будням без сохранения; отмена подтверждается штатным диалогом. `16b` — мобильные карточки клиентов и нижняя панель. DEMO обозначен самим приложением при включённых фикстурах. В общей демо-БД могут оставаться публичные ссылки и пометки LIVE от параллельного агента; они не подтверждают живой сбор в этом прогоне.

При недоступной production-сборке диагностический E2E допускает `E2E_DEV=true`, `NEXT_DIST_DIR=.next-qa-e2e`, `npx playwright test`. БД остаётся `crm_e2e`; это проверка dev-сервера, её нельзя выдавать за production build. Обычный `npx playwright test` по-прежнему использует `.next` и `next start`.

Команды выполняются в корне проекта. Нужны установленные зависимости, Chromium Playwright, заполненная `crm_demo` и уже применённая схема v2.4.1. Скрипты не запускают install, Prisma generate или migrate. Реальные персональные данные и ключ AI не нужны.

```powershell
npx next build
npx playwright test
```

E2E использует **только crm_e2e**, пересоздаёт её и копирует **только схему** из crm_demo через `pg_dump --schema-only`, затем выполняет обычный seed. Исходная crm_demo не очищается. PostgreSQL-контейнер по умолчанию `crm-test-testdb-1`, переопределение — `E2E_DB_CONTAINER`; URL тестовой БД — `E2E_DATABASE_URL` с обязательным именем `crm_e2e`. Это подготовка из существующей применённой схемы, а не проверка чистой установки миграций. Сервер E2E запускается на 3200 (`E2E_PORT`), AI отключён, скрапер работает на фикстурах, один worker. Notification проверяется реальным тактом генератора в отдельном процессе, без искусственной вставки уведомления.

В двух отдельных терминалах:

```powershell
npx tsx scripts/vkr/server.ts
```

```powershell
$env:VKR_AI_DEMO = 'true'
npx tsx scripts/vkr/server.ts
```

Первый процесс: 3210, AI выключен. Второй: 3211, AI включён **только для FakeResponsesProvider** и демонстрации веб-резерва. В обоих процессах `SCRAPER_DEMO_FIXTURES=true`, `SCRAPER_ENABLED=true`, `APP_TIMEZONE=Asia/Novosibirsk`. Ключ провайдера принудительно пустой. БД ограничена именем `crm_demo`; URL можно задать через `VKR_DATABASE_URL`, порт через `VKR_PORT`. StorageAdapter использует путь из существующей `.env.local`/`.env`, тот же, что использовался при demo seed.

В третьем терминале:

```powershell
npx tsx scripts/vkr/screenshots.ts
```

Логины и пароли читаются из `SEED_MANAGER_*` / `SEED_REALTOR1_*` без печати значений. Для этих двух синтетических пользователей в crm_demo снимается флаг обязательной смены seed-пароля; сами пароли не меняются. Генератор читает реальные ID записей, включая подхваченные прежним seed. Перед съёмкой веб-резерва руководитель временно меняет дневной лимит сотрудника через UI и возвращает его в `finally`. Каждый новый поиск сохраняется штатным API, поэтому при многократных повторах возможен честный отказ остальных дневных/часовых лимитов; не очищать журнал для сокрытия такого отказа. Подготовленный комплект фиксирует успешный демонстрационный веб-резерв, не доступность живого Yandex или площадок.

PNG и manifest: `docs/screenshots/vkr/`; описания с UTC-датой, HEAD, ролью, данными и режимом: `docs/vkr/screenshots.md`. Viewport 1440×900, мобильный 390×844; длинные страницы снимаются целиком с начала документа. Печать — реальный print CSS, загрузка и навигация ожидаются явно. Макеты, подмена ответов через Playwright и дорисовка интерфейса не используются.

Найденный в браузере дефект приложения: `/settings/ai` использовал несуществующий layout-класс `stack`, из-за чего поля/таблицы слипались. Исправление ограничено `settings/ai/page.tsx` и локальным `settings.module.css`; после свежей сборки экран проверен повторно. Бизнес-логика, схема и миграции не менялись.

## Полировка UI перед защитой

Демо-фикстуры площадок: `tests/fixtures/scraper/demo-novosibirsk/`; исходные unit-фикстуры остаются в родительской папке. `SCRAPER_DEMO_FIXTURES=true` использует новосибирский набор. Seed обновляет ранее созданные синтетические записи по связям, включая случайные ID раннего seed; повторный запуск сохраняет количество бизнес-записей. Для заполненной и мигрированной `crm_demo` достаточно `DATABASE_URL=…/crm_demo npm run db:seed:demo` (в PowerShell задайте переменную отдельно). Пересоздавать БД не требуется.

Все контексты съёмки используют `locale: ru-RU`, `timezoneId: Asia/Novosibirsk`. Кадр 08 — снимок самого блока подборки, остальные — окна или полные страницы. Перед снимком закрываются штатные тосты; скрытие UI через CSS не применяется. Генератор обновляет дату UTC, HEAD, контрольные суммы PNG в manifest и `SHA256SUMS`. Визуальную проверку каждого кадра выполняют отдельно после съёмки.

Проверки: `npx tsc --noEmit`, `npx eslint . --max-warnings=0`, `npm test`, `npx next build`, `npx playwright test`. E2E проверяет также русские файловые поля, выбор нескольких файлов, drag&drop, удаление из очереди, рабочие часы и tooltip календаря. В сквозном сценарии плотная группа событий раскрывается через «+ещё».

Повторные репетиции веб-резерва используют отдельный fake-only процесс с лимитом 30 веб-заданий в день (`scripts/vkr/server.ts`). Перед кадром 07 руководитель через UI временно задаёт 30 вызовов сотрудника и 60 агентства в сутки; исходные значения возвращаются в `finally`. Журнал затрат не очищается, реальные ключи принудительно отсутствуют. Это ограниченная конфигурация демонстрации, не изменение production-политики.
