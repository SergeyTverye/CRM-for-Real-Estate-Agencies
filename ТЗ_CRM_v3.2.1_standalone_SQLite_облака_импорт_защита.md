# Техническое задание v3.2.1. Автономная настольная CRM, резервирование и защищённый импорт Excel

**Проект:** CRM для ООО «Магазин недвижимости»  
**Основа:** ветка `feature/tz-v3.1`, коммит `e9d7dea`  
**Назначение:** автономный desktop-выпуск с сохранением серверной v3.1, защищённой обработкой рабочего Excel и ограниченной технической полировкой поиска/ИИ  
**Целевые ОС:** Windows 10 x64 (22H2) и Windows 11 x64  
**Основной результат:** один проверенный установщик `CRM-Setup-Windows-x64.exe` для самостоятельной установки руководителем без Docker, PostgreSQL-сервера, Node.js и терминала. Бизнес-операции доступны офлайн, облачные копии — после подключения провайдеров.

**Режим конфиденциальности:** рабочая книга `РЕКЛАМНЫЕ ОБЪЕКТЫ_РАБОТА.xlsx` — коммерческая тайна. Её содержимое запрещено отправлять сторонним моделям, в облачные AI API, бесплатным агентам, Git и CI-артефактам. Проверку проводят в доверенном локальном контуре. Фактическая структура книги определяется только после локального чтения файла.

**Правило приёмки:** выпуск desktop не допускает регрессии действующей многопользовательской PostgreSQL-версии. Проверка standalone и серверного режима — два обязательных набора тестов.

## 1. Цель, приоритеты, границы

### 1.1. Обязательный результат P0

1. **Tauri 2** как настольная оболочка существующего интерфейса, с локальным Next.js/Node.js и фоновыми задачами.
2. **SQLite как альтернативный backend** всех необходимых для повседневной эксплуатации модулей. PostgreSQL-вариант v3.1 сохранить как поддерживаемое серверное развёртывание.
3. **Полный автономный инсталлятор** с первым запуском, созданием локальной базы, ярлыком, диагностикой, обновлением и безопасным удалением программы без удаления данных.
4. **Резервное копирование и восстановление** согласованного набора «SQLite + документы/фото + необходимые метаданные» локально, на внешний HDD/USB, в Yandex Cloud Object Storage и Облако Mail.ru. Подключение каждого провайдера независимо, одновременная отправка в оба обязательна.
5. **Автоматическое восстановление обмена после отсутствия сети:** локальная CRM продолжает работать, архивы накапливаются в очереди и загружаются при появлении соединения.
6. **Перенос состояния между компьютерами** через USB или проверенный облачный снимок с контролем версий и запретом незаметной перезаписи расходящихся локальных изменений.
7. **Windows-сборка в GitHub Actions** и проверяемый EXE-артефакт.
8. **Полноценная деинсталляция** через системный список приложений Windows с корректным удалением процессов, ярлыков, записей реестра и принадлежащих программе компонентов. По умолчанию сохранять рабочие данные.
9. **Импорт и обратный экспорт коммерческого Excel** в обоих режимах установки, с локальной проверкой исходного файла, предпросмотром, защитой от дублей и сохранением структуры целевого Excel.
10. **Двойной регрессионный контур**: автономный SQLite и действующий многопользовательский PostgreSQL, включая обновления, миграции, права, отчёты, файлы и фоновые задания.

### 1.2. За пределами v3.2

- Полноценная **multi-writer**-синхронизация, когда несколько автономных устройств одновременно меняют одну общую базу и автоматически сливают записи на уровне полей. Для неё потребуется отдельное ТЗ с журналом событий, разрешением конфликтов и согласованием прав.
- Новая телефония, новые крупные бизнес-модули, изменение правил CRM и подключение площадок без разрешённого способа доступа. Точечные исправления скрапера и AI допускаются после P0 как P2 при наличии ресурсов (§12).
- Обязательные платные облачные сервисы для первого запуска. Облака подключаются добровольно и позже.
- Прямой запуск рабочего SQLite-файла из облачной/сетевой папки.

**Термины:** *backup* — самостоятельный проверенный архив для восстановления. *Репликация backup* — размещение одного архива на нескольких носителях. *Перенос состояния* — безопасная передача актуального снимка другому устройству. Эти операции не равны автоматическому объединению двух одновременно изменённых баз.

## 2. Отправная архитектура и принцип совместимости

Текущая v3.1: Next.js 16 / React 19, Node.js 24, Prisma 7, PostgreSQL 18, отдельные worker уведомлений и поиска, Chromium для некоторых сценариев, собственное файловое хранилище и механизмы backup/restore. По схеме GitHub на момент постановки задачи: **87 Prisma-моделей**, типы и миграции PostgreSQL, в том числе `pg_advisory_xact_lock` для бюджета ИИ. Прямое переключение одного `DATABASE_URL` на SQLite не допускается.

- Создать отдельную сборку `desktop`, сохранив сборку `server` и исходные API-контракты.
- Создать отдельную SQLite-схему, миграции и сгенерированный Prisma Client либо согласованный адаптерный слой. PostgreSQL-миграции не переписывать.
- Проверять расхождения в DTO, валидаторах Zod, внешних ключах, `UNIQUE`, правилах `ON DELETE`, датах, точных денежных значениях, JSON и правах доступа.
- Запретить зависимости desktop-кода от PostgreSQL-only SQL. Для блокировок, сериализации и атомарного AI-бюджета реализовать эквивалент на SQLite, с тестами параллельных запросов.
- Рассматривать сохранение прежней серверной версии как регрессионное требование.
- **Не менять единый production baseline PostgreSQL под SQLite.** Сохранить текущие `compose.yaml`, систему миграций PostgreSQL, `PrismaPg`, RBAC, маршруты API, очереди worker, резервирование расходов AI и restore. Ввести выбор адаптера исключительно по явному режиму `server`/`desktop`, не по случайному наличию файла БД.
- Зафиксировать состав сравнения: одинаковые запросы API и роли, контрольные сценарии CRM, таблицы/связи, сохранение и восстановление вложений, планировщик, экспорт, AI-права и журналы. Изменения общей доменной логики проверять на двух БД.
- На уровне кода запретить импорт `desktop-only` модулей из серверной сборки и обратные зависимости от SQLite-специфичных путей. Разделить генерацию Prisma Client и миграции без перезаписи исторических PG migration files. Поддерживать обновление ранее установленной server-версии v3.1.
- Зафиксировать нагрузочную проверку на трёх одновременных пользователях, транзакционную конкуренцию и изоляцию прав. Desktop разрешает однопользовательскую запись. Серверный режим сохраняет несколько рабочих мест с одной общей PostgreSQL-БД.

## 3. Настольная архитектура P0

**Tauri 2 → локальный интерфейс Next.js на loopback → сервисы CRM → SQLite и каталог файлов.**

- Tauri открывает интерфейс внутри WebView2 и управляет жизненным циклом приложения. Встроить Node.js 24 x64 и production Next.js в ресурсы установщика. Допускается бинарный sidecar или упакованный Node runtime с локальной сборкой `output: standalone`; выбор подтверждается запуском на чистой Windows.
- Перевести фоновые процессы уведомлений и поиска на управление desktop supervisor. Все процессы стартуют один раз и завершаются предсказуемо. Не допускать двойного выполнения при повторном клике по ярлыку.
- Сервер слушает только `127.0.0.1`, работает на обнаруженном свободном порту, подтверждает готовность через `/api/health/ready`. Порт и URL передавать оболочке безопасным способом, запретить доступ из LAN по умолчанию.
- Сохранить авторизацию CRM, роли, CSRF/Origin-проверки, ограничение CORS, приватность файлов и запрет выполнения произвольных команд через интерфейс Tauri. Локальный loopback сам по себе не заменяет проверку сессии.
- При закрытии окна предложить «Свернуть в область уведомлений» или «Завершить». В режиме tray продолжают работать напоминания и отложенный backup. При полном выходе процессы останавливаются, незавершённый архив остаётся в очереди.
- Не включать тестовые API-ключи или предопределённые пароли. На первом запуске руководитель создаёт пароль, программа формирует случайные идентификаторы и локальные секреты.
- Для desktop включить строгие capabilities Tauri и allowlist IPC/sidecar. Ограничить возможность запуска произвольного процесса и доступ к файловой системе. Защищать loopback-сервер от запросов чужих локальных веб-страниц (проверки Origin/Host/CSRF и привязка сессии), тестировать запуск нескольких окон и восстановление после аварий.
- Уведомления/задания должны иметь единый desktop-supervisor, защищённый от двойного запуска. Фоновые задачи и резервные копии работают лишь пока активен процесс приложения/tray. UI должен объяснять этот режим и показывать последний успешный запуск задания.
- Без интернета разрешены ручной импорт и экспорт Excel, все локальные формы/документы/каталог и восстановление с накопителя. При отсутствии сети сбой внешней площадки/ИИ не должен блокировать локальные операции.
- Для полностью офлайн-установки включить WebView2 offline installer или предварительно проверенный bundled runtime. Отдельно комплектовать нужный Chromium для PDF/скрапера либо доказать работоспособность без него. Никаких загрузок из интернета при установке и обычной офлайн-работе.

## 4. SQLite как полноценный альтернативный backend P0

### 4.1. Адаптация данных

- Использовать поддерживаемый Prisma 7 SQLite adapter (например, `@prisma/adapter-better-sqlite3`) и отдельный генератор клиентского кода.
- Перенести 87 моделей с сохранением бизнес-смысла. Заменить PG-specific типы, UUID по умолчанию, массивы, `JSONB`, таймзоны, операторы и raw SQL. Обоснованно вынести сложные массивы в связующие таблицы или сериализованный JSON с явной проверкой схемы.
- Сохранить UUID сущностей, связи, уникальность и защиту от дублей. Денежные суммы и стоимость AI хранить без ошибок двоичной арифметики, предпочтительно в целых минимальных единицах с проверяемой конвертацией.
- Даты хранить с единым правилом UTC/epoch, интерфейс использует `APP_TIMEZONE=Asia/Novosibirsk` по умолчанию. Проверить переходы суток/месяца и повторяющиеся задачи.
- Включить `foreign_keys=ON`, задать `busy_timeout`, использовать WAL только на локальном диске. Файл БД не держать в папке OneDrive/Яндекс.Диск/Облако Mail.ru.
- Обеспечить атомарные бизнес-операции и перенос существующей логики контроля конкурентных запросов, прав доступа и журнала аудита.

### 4.2. Перенос существующих данных

- Реализовать проверяемый инструмент **PostgreSQL → SQLite**: перенос исходных ID, всех значимых сущностей и связей, снимков поиска, AI-журналов, документов, версий шаблонов и файлового хранилища.
- Импорт должен выполнять предварительную проверку, создавать отчёт несовместимостей, запускаться в новой пустой SQLite и оставлять исходный PostgreSQL неизменным. При ошибке откатывать целевую установку до стартового состояния.
- Для первого запуска на новом ПК предусмотрены две опции: **«Пустая база»** и **«Демонстрационные данные»**. Импорт старой БД — отдельное действие администратора.
- Сверять количества записей по сущностям, выборочные связности, доступность документов по checksum, права ролей и суммарные финансовые значения.

## 5. Установщик и пользовательский сценарий P0

- Один `CRM-Setup-Windows-x64.exe`, installer Tauri NSIS, русскоязычные экраны. Установка **для текущего пользователя** без прав администратора, если системная конфигурация это допускает.
- Поддержка Windows 10 x64 22H2 и Windows 11 x64. До установки проверять архитектуру, объём диска и совместимость зависимостей. Точный минимальный объём ОЗУ и размер инсталлятора определить измерением и указать в README.
- Создать ярлык в меню «Пуск», опционально на рабочем столе. Открывать CRM после проверки готовности сервера. Показывать понятную диагностику, если старт не удался.
- Program files хранить отдельно от данных. Каталоги данных, например `%LOCALAPPDATA%\RealEstateCRM\data`, файлы `%LOCALAPPDATA%\RealEstateCRM\files`, архивы `%LOCALAPPDATA%\RealEstateCRM\backups`. Не привязывать пути к месту установки EXE.
- Систему можно использовать без сети: клиенты, задачи, планер, документы, локальные подборки/каталог, поиск по накопленной базе, экспорт XLSX/DOCX/PDF, журнал. Внешний поиск, Yandex AI и облачный обмен корректно показывают состояние «Нужен интернет» без блокировки остальной CRM.
- Предусмотреть независимое отключение AI/внешнего скрапера в настройках desktop.
- Обновление: защитный снимок → проверка совместимости → миграция SQLite → новый бинарный пакет → smoke → сохранение/откат при ошибке. Не стирать пользовательские файлы и учётные записи.
- Удаление программы по умолчанию сохраняет документы, БД и архивы. Отдельная операция полного удаления с предупреждением и подтверждением.

### 5.1. Деинсталляция и жизненный цикл установки — обязательный P0

- Зарегистрировать приложение в **Параметры Windows → Приложения → Установленные приложения** (и совместимой панели «Программы и компоненты»). Использовать штатную регистрацию NSIS/Tauri в `HKCU` для per-user установки, включая DisplayName, DisplayVersion, Publisher, DisplayIcon, InstallLocation и корректный UninstallString. Не создавать конкурирующих/осиротевших записей при обновлении.
- Поддержать удаление через Windows Settings и штатный uninstaller. Перед удалением закрывать WebView, локальный Node/Next.js, worker, Chromium, backup queue, файловые дескрипторы и задачи автозапуска. Удалить только принадлежащие приложению файлы программы, ярлыки, записи деинсталляции, собственные ключи автозапуска/службы/таски и временные каталоги. **Запрещено удалять общесистемный WebView2 или другие общие runtimes.**
- **Удаление по умолчанию — с сохранением данных.** Оставить `%LOCALAPPDATA%\RealEstateCRM\data`, файлы, шаблоны, SQLite, локальные резервные копии и recovery-инструкции. После удаления интерфейс должен объяснять, где остались данные и как восстановить CRM при повторной установке.
- **Полное удаление** — отдельный явный выбор с повторным подтверждением, предложением создать и проверить зашифрованную копию на внешнем носителе. Удалять только разрешённые каталоги текущего профиля и ключи приложения, не затрагивать облачные архивы, документы в произвольных папках пользователя и данные других программ. При ошибке удаления закрытых файлов сообщать список оставшихся элементов.
- Проверить обратимость установки: install → запуск → создание данных → uninstall с сохранением → reinstall → данные доступны, затем полный uninstall → остаточные процессы, задания, ярлыки и записи реестра отсутствуют. Обе ветки деинсталляции проверять на чистых Windows 10/11.
- NSIS hooks `PREUNINSTALL`/`POSTUNINSTALL` использовать для собственных процессов и ресурсов, исключив дублирование стандартного механизма Tauri. Обновление приложения не должно запускать полную очистку пользовательских данных. Логи удаления не содержат конфиденциальных сведений.

## 6. Единый формат резервной копии P0

Архив — переносимый, версионируемый, **зашифрованный** пакет, содержащий согласованный SQLite snapshot, документы/фотографии/шаблоны и необходимые настройки без паролей API и ключей облаков. Название, например `crm-backup-YYYYMMDD-HHMMSS-<id>.crmbackup`.

**Манифест:** `backupId`, версия формата, версия CRM/схемы, `deploymentId`, `instanceId`, `deviceId`, `snapshotRevision`, `createdAtUtc`, список включённых компонентов и файлов, размеры, SHA-256, тип шифрования, маркер полного/инкрементального архива, результат проверки, контрольная сумма манифеста.

- Использовать SQLite Online Backup API либо `VACUUM INTO` для согласованного снимка вместо копирования открытого `.db` средствами файловой системы.
- Перед сборкой пакета зафиксировать согласованное состояние DB и storage: краткая блокировка операций записи, согласование in-flight файлов, ожидание завершения операций или безопасная остановка/снимок с контрольными суммами. В backup не должны попасть «осиротевшие» документы или незавершённые версии.
- Реализовать полные архивы в MVP. Инкрементальное копирование допустимо в будущем после проверки восстановления полного цепочного набора.
- Шифровать локально **до отправки** в облако, аутентифицированное шифрование, защищённый KDF, случайные salt/nonce на каждый архив. Ключ восстановления выводится из кодовой фразы пользователя, не сохраняемой в облаке; локальные учётные данные сервисов хранить в Windows Credential Manager/DPAPI. Создать понятную процедуру экспорта recovery key на отдельный носитель.
- До объявления «Резервная копия готова» проверить целостность, контрольные суммы, открытие тестового снимка и наличие всех обязательных файлов. В интерфейсе отдельно показывать «Локальный архив готов», «Загружен в Яндекс», «Загружен в Mail», «USB готов».
- Поддержать политику хранения (по количеству/дням) отдельно для каждого направления, защиту хотя бы нескольких последних корректных поколений и запрет автоматического удаления последнего пригодного снимка.
- Отдельно проверять **атомарность набора БД + файлы**: файловые записи синхронизировать с checkpoint/revision БД, фиксировать manifest файлового каталога и все версии документов. Сбой в середине архива оставляет последнюю подтверждённую копию; неполную сборку помечать pending и удалять только после безопасной диагностики.
- В MVP использовать **полный** архив с контрольной суммой, а не обещать полноценные инкрементальные снимки. Формат архива versioned, с явным алгоритмом шифрования и authenticated encryption. Любые временные незашифрованные копии хранить в ACL-защищённом временном каталоге и безопасно убирать после завершения, с учётом особенностей SSD.
- **Восстановление:** сначала скачивание/чтение в staging, проверка целостности и версии схемы, расшифровка, контроль FK/`PRAGMA integrity_check`, контроль выборочных файлов и логических счётчиков. Затем защитный снимок текущего состояния, остановка worker/веб-сервера и атомарное применение. Отказ до переключения оставляет исходную базу пригодной.
- Предусмотреть восстановление при забытом пароле только при наличии сохранённого recovery key. Интерфейс требует отдельно подтвердить, что пользователь сохранил ключ восстановления. Не включать секрет шифрования в сам архив, облако или Github Actions.
- Ограничить число копий, пространство на локальном диске и очередь, запретить бесконечное накопление новых архивов при длительном отказе облака. Не удалять последний пригодный локальный backup при очистке. Время и фактическую пригодность определять восстановлением, а не только успешным HTTP PUT.

## 7. Облачные назначения P0

### 7.1. Yandex Cloud Object Storage

- Использовать S3-совместимый API **Yandex Cloud Object Storage**. Облако Яндекса здесь означает Object Storage, а не Яндекс.Диск.
- В мастере подключения руководитель указывает bucket, регион/endpoint при необходимости, учётные данные сервисного аккаунта с минимальными правами и отдельный префикс установки. UI должен иметь «Проверить подключение», «Сделать тестовую копию», «Открыть список копий», «Восстановить».
- Защитить секреты в Windows Credential Manager/DPAPI, использовать TLS, не включать их в архивы, логи, crash reports и GitHub artifacts.
- Использовать endpoint `https://storage.yandexcloud.net`, AWS Signature V4 и **статический ключ сервисного аккаунта** с ограниченными ролями/политикой на конкретный bucket и префикс. Запретить анонимное чтение/list, bucket-wide `storage.admin` для рабочего клиента и публикацию ключа в EXE. В GUI — проверка подключения и диагностика отсутствия разрешений.
- Писать архивы под уникальными неизменяемыми именами `backupId`, `If-None-Match: *` для защиты от перезаписи; при обновлении отдельного указателя `latest` использовать `If-Match` с ETag либо обходиться без общего mutable pointer. ETag не считать заменой SHA-256 архива. При необходимости больших файлов поддержать multipart upload с отменой незавершённых загрузок.
- Предусмотреть версионирование и lifecycle-правила как **рекомендуемую опцию**, с предупреждением о дополнительных расходах на старые версии и операции. Настройки срока хранения не должны удалять последний подтверждённый snapshot.
- Тестировать доступ к бакету с минимальными ролями, отсутствие прав, повторную отправку, потерю сети при multipart, повторное скачивание и реальный restore. Назначение Yandex Object Storage отделять от Yandex AI Studio и Яндекс.Диска.

### 7.2. Облако Mail.ru

- Использовать официально поддерживаемый **WebDAV `https://webdav.cloud.mail.ru`** с отдельным паролем внешнего приложения либо проверенный `rclone mailru` backend. Пользователь должен иметь возможность подключиться в GUI без терминала.
- Проверить актуальные ограничения размера файла, квоты, ошибок сети и поведения перезаписи. Разбивать архив на части только при необходимости, с манифестом и полной проверкой обратной сборки.
- Если применён `rclone`, упаковать допустимый для распространения исполняемый файл и лицензионные уведомления в дистрибутив. Не требовать системного `rclone`.
- Прямой WebDAV-клиент через HTTPS использует `PROPFIND`, `MKCOL`, `PUT`, `GET`, `DELETE` и, если поддерживается, `MOVE`. Авторизация — email и **пароль для внешнего приложения**, без сохранения основного пароля Mail. Работа через API не должна требовать монтирования сетевого диска Windows или отдельной настройки службы WebClient.
- Фактическую поддержку HTTP-методов, коды ответов, лимит размера, запрет/разрешение перезаписи, поведение `MOVE`, квоту и rate-limit проверить на пользовательском аккаунте **без включения коммерческого Excel**. Не предполагать гарантии атомарного переименования у WebDAV.
- Загружать архив в уникальный временный remote-key, при поддержке безопасного переименования публиковать финальное имя после проверки. В любом случае окончательный manifest со статусом complete публиковать последним. Полностью скачивать контрольный архив на тесте и сверять SHA-256 после расшифровки, так как слабая/отсутствующая ETag-семантика не гарантирует целостности.
- Не использовать WebDAV LOCK как единственный механизм распределённой блокировки. Если сервис не гарантирует условную запись, синхронизация с Mail.ru допускает **обмен архивами с обнаружением расхождения** без автоматического назначения общей самой новой версии по времени.

### 7.3. Работа обоих облаков

- Поддерживать любое сочетание: только Яндекс, только Mail.ru, **оба одновременно**, ни одного (USB/локально).
- Создать один проверенный зашифрованный backup и независимо передать одинаковый `backupId` и checksum всем выбранным destinations. Раздельные статусы, очередь, ограниченные retry с backoff, ручной повтор только неудачного направления.
- Частичный успех явно обозначать: «Яндекс — успешно, Mail.ru — ошибка». Успех одного облака не удаляет локальный архив и не маскирует ошибку второго.
- Периодическое резервное копирование: настройка времени/частоты, копия при закрытии по желанию, копия перед обновлением и ручная кнопка «Создать резервную копию сейчас». При отсутствии интернета копия хранится локально и автоматически передаётся после восстановления связи, когда программа/фоновый процесс работает.
- Восстановление возможно из **любого одного** облака, даже если второе недоступно. Последнюю подтверждённо пригодную копию показывать вместе с датой/версиями и местом хранения.
- Загрузка в облако проходит ступени `queued → uploading → uploaded → verified` либо `failed`, отдельно для каждого направления. После перезапуска очередь поднимает незавершённые передачи идемпотентно. Успех — только после проверки существования объекта, длины и контрольной суммы при контрольном скачивании. Фактический restore проверяют отдельным тестом.
- Для `Yandex + Mail.ru` использовать **один и тот же зашифрованный поток**, с общим manifest/hash. Сбой одного назначения не отменяет подтверждённый результат второго. Проверять два восстановления по отдельности, включая случай потери учётных данных одного сервиса.
- Расписание backup ориентируется на локальный часовой пояс, учитывает сон Windows, выключенный ПК и пропущенные интервалы. После запуска восполняет пропущенное максимум одним контролируемым заданием, исключая шторм архивов.
- Привести в UI прогноз стоимости Yandex Object Storage и потребления квоты Mail.ru там, где API/тариф позволяют получить данные. Не утверждать, что резервное копирование в Object Storage бесплатно.

## 8. Офлайн HDD / USB P0

- Действия «Экспортировать резервную копию на накопитель» и «Восстановить из файла». Пользователь выбирает путь через системный диалог.
- Проверить объём свободного места, права записи, недоступность/внезапное извлечение, завершённость пакета. Писать во временный файл, проверять SHA-256 и переименовывать в итоговый только после успешной записи. Повторные операции идемпотентны.
- Восстановление доступно на другом компьютере с такой же или совместимой более новой версией. Не требовать доступа к облакам. Подтверждение и защитная локальная копия перед заменой данных обязательны.
- Нельзя выдавать неудавшийся копируемый файл за полный архив или автоматически удалять исходные данные после экспорта.

## 9. Передача состояния между standalone-установками P0

**Первый поддерживаемый режим — последовательная работа с одной логической базой (single-writer handoff).** Например, руководитель завершила работу на ноутбуке, отправила архив в облако, затем загрузила его на другой ПК и продолжила работу.

- У каждого рабочего пространства есть `deploymentId`, уникальные `instanceId/deviceId`, монотонная `snapshotRevision`, `parentBackupId`. Локальная установка хранит последний импортированный источник и маркер собственных изменений после него.
- Операции «Передать состояние», «Получить состояние», «Сравнить с локальной версией». Перед переносом создаётся проверенный снимок, после импорта выполняется атомарная замена с предварительным локальным backup и миграциями по необходимости.
- Если на целевом ПК появились собственные изменения после последней общей версии или обнаружены две расходящиеся ветви, **запретить автоматическую замену/merge**. Показать «Конфликт версий», сохранить обе копии и предложить открыть отдельную копию для просмотра или выбрать восстановление вручную с подтверждением.
- Нельзя опираться только на часы устройств. Учитывать идентификатор родительского снимка, ревизии и контрольные суммы. Отсутствие сети не должно блокировать обычную работу локальной CRM, но её последующий экспорт может вызвать конфликт.
- Если один из облачных провайдеров отстаёт, показывать задержку и предлагать восстановление из последнего проверенного общего/более нового архива. **Автоматического двустороннего слияния рабочих записей в v3.2.1 нет.**
- Для одновременной работы руководителя и двух риелторов с одной базой сохраняется серверная PostgreSQL-версия v3.1. В документации и UI это ограничение объяснить простым языком.
- В режиме передачи состояния определить **проверяемый протокол владения**: при выдаче снимка источник переходит в режим просмотра либо явно сообщает, что последующая работа на нём создаст расходящуюся ветвь. Новый компьютер проверяет общую исходную ревизию и факт последних локальных изменений. Нельзя обещать глобальную эксклюзивность без сети: офлайн-компьютеры могут нарушить очередь владения.
- Для Yandex S3 использовать атомарное условное обновление маркера владения при доступности сети, но **не считать его распределённым замком на период полной офлайн-работы**. В Mail WebDAV при отсутствии CAS запретить автоматическое повышение «новейшего» снимка до единственного общего источника.
- При реальном расхождении предложить два явных пути: оставить обе независимые базы для просмотра или выполнить ручной перенос с архивированием проигрывающей версии и подтверждением руководителя. **Поэлементного слияния клиентов, задач и сделок в v3.2.1 нет.** Не выдавать такой перенос за многопользовательскую синхронизацию.
- Перенос через USB должен проходить те же проверки `backupId`, `parentBackupId`, `revision` и SHA-256, что облачный перенос.

## 10. Интерфейс руководителя P0

Раздел **«Локальная установка и резервные копии»**:

- Статус «Работает локально», версия, размещение данных, объём, последнее сохранение и результат самопроверки.
- Плитки «Яндекс Облако», «Облако Mail.ru», «USB/HDD» с независимым подключением, индикатором результата и датой последней проверенной копии.
- Кнопки «Создать копию», «Настроить расписание», «Восстановить», «Экспорт на накопитель», «Перенести работу на другой компьютер», «Проверить архив».
- Понятный журнал попыток, объём и время, причина отказа, состояние очереди и повтор.
- Предупреждение при отключённом шифровании (в MVP шифрование архивов обязательно), забытом recovery key, полном диске, недоступном интернете, неверных учётных данных и конфликте версий.
- Штатные модули CRM доступны и без облачного подключения. На первом запуске мастер не заставляет руководителя заводить аккаунты в облаках.

## 11. Безопасность и эксплуатационные требования

- По умолчанию нет публикации локального сервера в локальную сеть или интернет. Защита loopback API от CSRF и обращений чужих веб-страниц, безопасные cookies и роли пользователей сохраняются.
- Защитить файл SQLite и конфигурацию ACL текущего Windows-пользователя. Пароли и токены не сохранять открытым текстом; журналировать лишь безопасные коды ошибок.
- Проверять backup от изменения/подмены и ограничивать пути распаковки (path traversal, symlink, zip bomb, слишком большие файлы). Восстановление выполнять в отдельный staging-каталог, затем атомарно переключать данные.
- Сбой питания, закрытие программы во время экспорта, обрыв связи и тайм-аут провайдера не должны приводить к потере последнего корректного состояния.
- Облачные квоты и расходы показывать отдельно от бюджета Yandex AI. Платное подключение Yandex Cloud Object Storage не входит в обязательную установку.
- Дистрибутив должен иметь SBOM/список встроенных runtimes и лицензий, checksum SHA-256. Code signing предпочтителен при наличии сертификата, отсутствие подписи и предупреждения Windows SmartScreen отразить в инструкции.
- Система хранит только необходимое для desktop в отдельном профиле пользователя. Службы/задания, если потребуются, регистрировать лишь в пределах выбранной установки и удалять со всеми ссылками. Отключение Windows Defender, защит браузера, фаервола или UAC запрещено.
- CI/CD работает на **синтетических** данных. Запретить добавление приватных исходных Excel, снимков рабочих БД, ZIP с клиентскими файлами, ключей облаков и реальных записей в Docker context, MSI/NSIS resources, артефакты, дампы памяти и отчёты тестов.
- Ограниченный доступ к материалам enterprise-импорта описан в §12. Передача реального Excel любому LLM, сторонним сервисам разметки/обработки или бесплатным безлимитным агентам запрещена без отдельного прямого разрешения владельца данных.

## 12. Реальный Excel предприятия и ограниченная полировка поиска/ИИ

### 12.1. Конфиденциальный рабочий файл — обязательный P0

**Вход:** `РЕКЛАМНЫЕ ОБЪЕКТЫ_РАБОТА.xlsx`. Файл содержит коммерчески значимые сведения и рассматривается как закрытая информация заказчика. Его фактические листы, заголовки и типы колонок определяет локальный проверяющий **после получения файла**, без предположений о структуре. До фактического чтения объявлять импорт этого файла пройденным запрещено.

- **Сначала защитить Git:** в корневую `.gitignore` до копирования файла в рабочую папку добавить как минимум:

  ```gitignore
  # Confidential enterprise workbook and its Office lock files
  РЕКЛАМНЫЕ ОБЪЕКТЫ_РАБОТА.xlsx
  **/РЕКЛАМНЫЕ ОБЪЕКТЫ_РАБОТА.xlsx
  ~$РЕКЛАМНЫЕ ОБЪЕКТЫ_РАБОТА.xlsx
  **/~$РЕКЛАМНЫЕ ОБЪЕКТЫ_РАБОТА.xlsx
  /private-data/
  /data/private-imports/
  ```

  Gitignore не защищает ранее отслеживаемые файлы. До начала теста проверить `git ls-files --error-unmatch -- "РЕКЛАМНЫЕ ОБЪЕКТЫ_РАБОТА.xlsx"` и все возможные относительные пути. В случае обнаружения отслеживания прекратить работу, исключить файл из индекса без удаления локальной копии, оценить необходимость очистки истории и ротации уже раскрытых секретов. Дополнительно проверить `git status --ignored`, `git check-ignore -v` и staged diff. Установить pre-commit/CI проверку по имени, расширению, путям и содержимому артефактов, не полагаясь исключительно на `.gitignore`.
- Оригинал хранить только в защищённом локальном каталоге с ACL текущего Windows-пользователя. Сначала создать отдельную защищённую рабочую копию и вычислить SHA-256 **локально**. В репозиторий допускаются только синтетические фикстуры без копирования реальных имён, телефонов, адресов и коммерческих сведений.
- Реальный файл обрабатывать только доверенным локальным импортёром на пользовательской/изолированной машине. **Запрещена передача содержимого, строк, скриншотов и вложений в сторонние модели, бесплатные безлимитные модели, Yandex AI, публичные API, GitHub Actions и облачные CI.** Разрешённые пользовательские зашифрованные резервные копии хранятся в его собственных облачных аккаунтах по настройкам backup.
- Локально изучить количество листов, блоков/таблиц, заголовки, объединённые ячейки, скрытые колонки/листы, формулы и их значения, стили, даты, комментарии, гиперссылки, изображения и возможные дубли. По результату составить **не содержащий записей заказчика** профиль полей, типов, обязательности, правил нормализации и исключений. Непонятные колонки оставлять `unresolved`, требуя подтверждения пользователя.
- Реализовать импорт через **предпросмотр (dry-run) → проверка ошибок/дублей → явный commit**. Сохранять связь с источником, исходный лист/ячейку в закрытом внутреннем журнале импорта, версии mapping и checksum входного файла. Повтор того же файла и повтор после сбоя не создают повторных клиентов, объектов или документов. Исключённые политикой персональные поля не попадут в БД, журнал, preview и отчёты.
- Корректно обрабатывать денежные значения, форматы дат Excel, формулы и кешированные значения, пустые и объединённые ячейки, скрытые строки, кириллицу, неоднозначные разделители и номера телефонов. Не вычислять произвольные макросы и не выполнять внешние ссылки. Тестировать в том числе намеренно повреждённую книгу и отказ половины строк.
- **Обратный экспорт:** отдельный режим «В формат рабочего Excel». Заполнять **копию исходного шаблона структуры** с согласованными листами и заголовками, сохранять поддерживаемую ширину столбцов, типы, фильтры, форматирование и формулы при согласованной схеме. Для колонок без источника данных оставлять безопасно пусто и выводить отчёт несовместимостей. Дополнительный универсальный XLSX/CSV экспорт сохраняется. Не заявлять гарантии полного бинарного тождества исходной Excel-книге.
- Сверить импорт/экспорт на локальной копии: количество распознанных строк, количество успешно импортированных, исключённых, отклонённых, причины, исходные идентификаторы, число листов, точность чисел/дат, контроль выбранных строк и повторный импорт **экспортированного** файла без дублей. Отчёт содержит агрегаты и обезличенные коды ошибок без фрагментов коммерческих строк.
- Проверять импорт и экспорт **в SQLite desktop и PostgreSQL server**, включая роль руководителя и отсутствие доступа у риелтора к закрытым данным других сотрудников. Не заменять рабочую БД демонстрационной. Результат приёмки хранить локально, в Git передавать лишь полностью обезличенный итог.

### 12.2. Скрапер и Yandex AI — P2 при наличии ресурсов

После выполнения обязательных DT и сохранения зелёного двойного regression gate разрешено точечно улучшать уже реализованные функции v3.1:

- Доработать реальные фильтры по назначению, дате публикации и первому обнаружению CRM, цене, площади, районам, этажу, признакам собственника и обязательным характеристикам. Не смешивать неизвестные даты и подтвердившуюся свежесть. Улучшать сортировки, группировку межплощадочных дублей, ручной импорт по URL и XLSX/CSV, полноту и причину отказа площадки.
- Исправлять нестабильные HTTP/парсерные сценарии на сохранённых разрешённых ответах, добавлять регулируемые задержки, очереди, ограниченные retry, диагностику CAPTCHA/403/429 и безопасное возобновление. Поиск разрешённых официальных API/экспортов и **ручное прохождение CAPTCHA пользователем там, где площадка это разрешает**, допустим. Автоматическое решение чужой CAPTCHA, подмена идентичности, обход ограничений доступа и запретов площадки не входят в задание.
- Повысить бизнес-полезность AI-анализа: точные доказательства из объявлений, неизвестные значения, логическая фильтрация жилых объектов, дедупликация, объяснение соответствия и сравнение; кеширование и контроль стоимости без отправки конфиденциального Excel или клиентских ПДн.
- Прогонять только ограниченное число платных LIVE-вызовов после установки/проверки бюджета. Все регрессионные исключения, тайм-ауты и конфликты тестировать на fake/REPLAY. Отдельно документировать `LIVE / REPLAY / DEMO`, источники и качество поиска. Не превращать P2 в условие завершения installer/backup этапа.

## 14. Реализация по зависимостям и конечные артефакты

1. Сохранить контрольный PostgreSQL baseline, выделить SQLite-модель и адаптеры. В первую очередь проверить сложные PG-only SQL/транзакции и основной CRM-путь. Не развивать Tauri до доказанной работоспособности ядра на SQLite.
2. Собрать локальный Next.js + workers + Chromium и оболочку Tauri, обеспечить offline-бандл Windows 10/11, первый запуск и пути данных.
3. Реализовать единый backup-архив, экспорт на USB и restore. Проверить на нескольких снимках и больших файловых вложениях.
4. Подключить Yandex Object Storage и Mail.ru Cloud с независимыми статусами, очередями и настройками. Проверить реальное скачивание и восстановление на пустой машине.
5. Добавить последовательный перенос состояния между двумя установками и обнаружение расхождения. Пройти DT-13/14 на отдельных базах.
6. Завершить проверки Windows-uninstall, двойной regression gate, Git-защиты и импорта/экспорта закрытой рабочей книги в доверенном локальном контуре.
7. Настроить GitHub Actions с синтетическими данными, подписать при наличии сертификата, выполнить DT-01…DT-27 и передать руководителю EXE.

**В Git:** отдельная ветка `feature/desktop-v3.2`, исходники Tauri, SQLite-схема и миграции, скрипты пакетирования, тесты, `docs/acceptance/desktop-v32/`, протокол установки, инструкции «Установить за несколько кликов», «Сделать копию», «Восстановить», «Перенести на другой ПК».

**Выход:** `CRM-Setup-Windows-x64.exe`, SHA-256, GitHub Actions artifact или Release, таблица прохождения DT-01…DT-27, доказательства фактического восстановления из каждого облака, тестовая демонстрационная база, скриншоты рабочего окна и настроек резервного копирования. Успех сборки EXE без испытания на чистом ПК не закрывает задачу.

## 15. Условия приёмки и реалистичные ограничения

**v3.2.1 завершена только после PASS обязательных DT-01…DT-27.** Если конкретное внешнее облако недоступно по объективной причине, статус остаётся BLOCKED с логом и воспроизводимым альтернативным способом (USB/другое облако), но требование поддержки этого облака не объявляется выполненным.

**Ключевая продуктовая граница:** пользователь может пользоваться установленной CRM полностью автономно, сохранять её резервные копии на USB и в два облака, восстанавливать и последовательно переносить рабочую базу на другой компьютер. Одновременные независимые изменения у нескольких сотрудников не объединяются автоматически. При необходимости коллективной работы действует серверная PostgreSQL-установка.
