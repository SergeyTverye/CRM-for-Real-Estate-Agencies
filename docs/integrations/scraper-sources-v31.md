## Контракт дат

`listing-dates.ts`: `parseSourceDate(value, fetchedAt)` и `extractListingDates(source, payload, {id?, url}, fetchedAt)`.

Нормализация возвращает `publishedAt: string|null`, `sourceUpdatedAt: string|null`, `dateSource: unknown | <source>:structured:publication | <source>:structured:update | <source>:html_label:publication | <source>:html_label:update`, `datePrecision: exact|day|unknown`. ISO-строки хранят момент UTC. `day` — начало календарного дня Asia/Novosibirsk (UTC+07), **не точное время публикации**. Относительные `сегодня`, `вчера`, `N дней назад` считаются от `fetchedAt`; «24 часа» должен отдельно фильтровать application. Поддержаны ISO с зоной/без зоны, epoch seconds/ms, `ДД.ММ.ГГГГ`, русский месяц, явные часы/минуты. Неоднозначные, невозможные и неподписанные даты → unknown.

`dateSource/datePrecision` относятся к публикации, если она известна; иначе к известному обновлению. Когда обе даты null, оба атрибута unknown. Обновление не заполняет `publishedAt`. `firstSeenAt/lastSeenAt` устанавливает БД/application; адаптер их не выдумывает. Сопоставление только по собственному ID/URL, включая родительскую карточку групповых помещений Циана. JSON/SSR читается как данные, без `eval` и исполнения скриптов. Строки `undefined` внутри JSON-строк не меняются.

## Управление нагрузкой и отказами

`source-limits.ts`: консервативные серверные пределы таблицы. Дефолт 2 страницы/100 карточек сохранён; `ScraperOptions.depth` и `sourceDepth[source]` переопределяют запрос в пределах потолка. ENV `SCRAPER_<SOURCE>_MAX_PAGES`, `SCRAPER_<SOURCE>_MAX_LISTINGS` может только **понижать** потолок. Например `SCRAPER_CIAN_MAX_PAGES=1`. ENV-файл в этой задаче не менялся. `buildScraperQuery(..., depth?)` принимает те же управляемые параметры.

`estimatedRequests` — верхняя оценка основных HTTP-запросов: число ветвей × страницы × коэффициент источника + setup; браузерные ресурсы в оценку не входят. Это не точный счётчик сети. `maxPages` ограничивает каждую OR-ветвь, `limit` — весь источник. На OnRealt пять назначений означают до пяти ветвей. Максимальная параллельность процессового адаптера 3 (дефолт 1), общий дедлайн максимум 300000 мс (дефолт 180000). Время в очереди входит в дедлайн; истечение/отмена удаляет ожидающий элемент, не дожидаясь чужого зависшего задания.

`searchDetailed(filters, {signal?, deadline?})` возвращает `AdapterSearchResult`. Поля источника: `status`, `resultCount`, `incomplete`, `pagesFetched` (успешные страницы всех ветвей), `listingsFetched` (кандидаты до нормализации), `maxPages`, `limit`, `estimatedRequests`, `reason`, опциональные `failureCode/actionUrl`. Ограничение определяется по **последней странице каждой ветви**, а не по наличию любой промежуточной next-ссылки. `hasNext=null`, ошибки, невалидные записи и отсечение делают охват неполным. Сортировка сайта по дате не гарантируется ни для одного текущего mapping; причина ограничения сообщает об этом. Сохранённую выборку сортирует application.

Статусы v3.1: success, partial, needs_user_action, rate_limited, blocked, parse_failed, timeout, cancelled, unsupported_filter, error, disabled. При сохранённых карточках и ошибке остаётся partial с причиной/кодом и actionUrl для CAPTCHA. `actionUrl` содержит только HTTPS-хост, без query, пути, cookies и токенов. Ошибки не возвращают upstream-текст.

Совместимый `search()` пока возвращает старый `SearchResult`: needs_user_action/rate_limited → blocked, parse_failed → error, cancelled → timeout; дополнительно сохраняет фактический `adapterStatus` и остальные metadata. **Агент application/UI должен подключить `searchDetailed` после расширения codebook/схемы**, иначе новые статусы не будут доступны через старый контракт. Нормализованные даты возвращаются в обоих методах. Сохранение дат и глубины — задача агента модели/application.

429: принимаются seconds и HTTP-date `Retry-After`. Только один отложенный повтор, минимальная пауза 1 с, только если она с резервом помещается в дедлайн. Нет/неверный заголовок, повторный 429 или недостаток времени → rate_limited. После блокировки/429/CAPTCHA новые ветви этого транспорта не обращаются к сети. 401/403/439 → blocked, явная проверка в HTML/URL → needs_user_action. Проверка отделена от упоминания captcha-библиотеки в обычной странице. Пользователь ничего не решает автоматически.

Обычный Playwright Chromium заменяет helper запуска пакета: helper содержал изменение webdriver/флаг скрытия автоматизации. Контекст CRM таких изменений не делает. HTTP и каждый redirect остаются DNS-pinned SSRF guarded, browser HTTP/subresources получают общий AbortSignal; service workers и WebSocket блокируются. `close()` в finally ограничен 1 с ожидания; поздно завершившийся launch также закрывается. Нужна обычная изоляция egress контейнера, как описано в `scraper.md`.

Парсеры расширяются локально через `extendSourceParsers`, `node_modules` не меняется. `searchPages` накапливается постранично, поэтому отмена следующей страницы сохраняет предыдущие результаты. Очередь адаптера **process-local**; персистентные job state, дедупликация повторного нажатия, восстановление после рестарта и последний успешный запуск принадлежат application/worker, здесь не реализуются.

## Запасной путь для агента API/UI

- `manual-listing.ts`: `addListingByUrl(url, {signal?, timeoutMs?, fetchedAt?}) → {status:'success', listing} | {status:'manual_required', source, url, reason}`. Только HTTPS известных площадок, порт 443, без credentials; query/hash удаляются. Один GET без повторов, общий SSRF/DNS/redirect guard; карточка извлекается парсером площадки либо собственным JSON-LD parser. Соседние рекомендации не принимаются за запрошенную карточку. Неизвестные операция, тип и цена сохраняются неизвестными.
- При manual_required API/UI показывает форму полей `manualListingSchema` (URL, заголовок, операция, тип, цена, ценовой текст/период, площадь, город, адрес, описание). `manualListing(input)` валидирует и формирует кандидата с `manualEntry=true`, неизвестной датой и неподтверждённым продавцом. Подтверждение и RBAC выполняются application. Storage path не возвращается; HTML не исполняется.
- `official-feed.ts`: `importOfficialFeed(Buffer, {format:'csv'|'xlsx'|'xml', source, fetchedAt?, maxRows?}) → {listings, pending, errors:[{row,code}], rowsRead, incomplete}`. Только preview, без записи в БД и сетевых обращений. До 10 МБ файла, 1000 строк по умолчанию, максимум 5000; XLSX проверяет суммарный распакованный размер ZIP ≤40 МБ и ≤2000 entries до ExcelJS. XML запрещает DTD/entities. CSV поддерживает UTF-8 BOM, запятую/точку с запятой, кавычки.
- Подмножество Яндекс XML: offer/internal-id, type, commercial-type/category, url, price/value, area/value, location/locality-name/address, creation-date, last-update-date. Avito Autoload: Ads/Ad, Id, Title, OperationType, ObjectType/CommercialType, Price, Square/Area, City, Address, опциональный Url/AdUrl. CSV/XLSX принимают те же имена и русские URL/Ссылка, Заголовок, Операция, Тип, Цена, Площадь, Город, Адрес. Это распознавание основных полей, не полная сертификация всех версий фидов.
- Autoload `Id` — внешний ID агентства, его нельзя выдавать за публичный ID Авито. Строки без URL возвращаются в `pending` с `externalId`, распознанными основными полями и `public_url_required`; UI предлагает указать публичную ссылку. Привязку к платформенной карточке не выдумываем. Поддеревья продавца/телефонов не маппируются. Ошибки содержат только строку/код, без исходных данных. Редактирование/подтверждение сотрудником и сохранение подключает application.
