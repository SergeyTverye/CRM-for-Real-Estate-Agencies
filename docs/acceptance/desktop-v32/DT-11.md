Фактический результат: [LIVE модуль](cloud-module-live.md) PASS — один архив 7 354 253 байта передан в оба облака, два восстановления с контролем БД и SHA файла. Два инъецированных отказа, queue reload и retry только ошибочного направления PASS. Историческое модульное доказательство остаётся в силе.

Установленный прогон a4 теперь подтверждает тот же архив в обоих направлениях: ID `5299d5d2-9789-4c04-90cb-727a54aaa2ff`, размер 2 111 322 байт, SHA-256 `5a92d2d59cb908cd476effc240b4d400e9f0e0cdac6449ec4b0be7c1c1fc495d`; verified в Yandex Object Storage и Облаке Mail.ru; destination-specific supervised restores из каждого облака после изменения синтетического клиента с восстановлением record projection и документа 262 144 байт. Фактическое восстановление из облака в установленной CRM теперь подтверждено. Подробности: [installed-a4-cloud.md](installed-a4-cloud.md).

Независимый fault-прогон на том же installed a4 (`run-bf1bf751-3743-420b-bff2-a8581677cc62`) дополнительно подтвердил изоляцию отказа: synthetic wrong S3 key ID привёл к ошибке Yandex Object Storage при успешной проверке Облака Mail.ru; после восстановления реальной конфигурации через UI retry поставлен в очередь, тот же архив `163d9223-27b4-41fe-8119-ed819074a7ba` (2 111 322 байт, SHA-256 `e9d9d4bf894e5420b5e835e5164c54451a45589540b26cc8c159e85d5338b7e4`) прошёл verify в обоих направлениях; выполнены destination-specific supervised restores из обоих провайдеров, record projection и SHA файла совпали; перезапуск и teardown PASS. Покрытие `INJECTED_SYNTHETIC_S3_KEY_ID_NOT_PHYSICAL_NETWORK_CUT`; физический обрыв сети, offline queue (DT-12) и обратный отказ не проверялись.
