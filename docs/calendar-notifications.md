# Календарь и уведомления — ТЗ v2.4.1 §8

## Использование

`/calendar`: день, неделя, месяц и повестка; фильтры сотрудника, типа и статуса. Даты отображаются в `APP_TIMEZONE` через `tz()`; для Asia/Novosibirsk это UTC+7 независимо от пояса браузера. FullCalendar 6 использует UTC только как координату отображения: API получает настоящие UTC-моменты, преобразование выполняется на обеих границах. В общей рабочей копии все шесть пакетов FullCalendar согласованы на 6.1.22. Официальные правила: <https://legacy.fullcalendar.io/docs/v6/react>, <https://legacy.fullcalendar.io/docs/v6/timeZone>.

Задача отображается по сроку, показ — по назначенному времени. Служебная задача `showing_or_meeting`, связанная с показом, исключена из календаря и генерации напоминаний, чтобы показ не дублировался. Перенос проходит через `updateTask`/`updateShowing`. Встречи можно создавать, редактировать и архивировать; используются проверки версии `expectedUpdatedAt`, аудит и проверка доступности CRM-ссылок. Повторения — `FREQ=DAILY|WEEKLY|MONTHLY`, необязательный `;UNTIL=YYYYMMDDTHHmmssZ`. UNTIL включительно, отсутствующие дни месяца пропускаются. Изменение повторяющейся записи изменяет серию; drag для неё отключён. Предупреждение о пересечении проверяет интервальные встречи, для новой повторяющейся серии — горизонт 90 дней.

Чужие личные встречи, включая просмотр руководителем, показываются как «Занято»: без описания, CRM-ссылок, версии и возможности редактирования. Общая встреча с недоступными связанными клиентом/потребностью/сделкой также становится «Занято». Названия задач раскрываются только при доступности связанных клиентских контекстов; иначе используется нейтральное название.

На `/today` сохранены действующие просроченные задачи; добавлена повестка, ближайшие показы, личные записи и рабочие свободные интервалы 09:00–18:00. Task.dueAt и показы без длительности не уменьшают свободное время. Быстрое завершение задачи сохраняет действующие инварианты потребностей: при необходимости продолжения сервис отклонит завершение без следующего действия.

`/notifications`: список с пагинацией, чтение одного/всех, snooze и переход к источнику. Настройка пользователя — 0/15/60/1440 или произвольное число минут (до года). Ежегодные и постсделочные контакты используют существующие Task, отдельные задачи-копии не создаются. Тексты уведомлений нейтральны; сохранённые произвольные title/link не возвращаются без реконструкции. Доступ к источнику повторно проверяется при чтении и изменении уведомления.

## API

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/v1/calendar?from=ISO&to=ISO&employee=UUID&type=...&status=...` | События в диапазоне до 100 дней |
| POST | `/api/v1/calendar` | `{type: task|showing|calendar_event, data: ...}` через действующие сервисы |
| POST | `/api/v1/calendar/move` | `{type,id,startAt,endAt?,expectedUpdatedAt}` |
| POST | `/api/v1/calendar/events` | Создать встречу |
| GET/PATCH/DELETE | `/api/v1/calendar/events/:id` | Получить/сохранить/архивировать; изменения с версией |
| GET | `/api/v1/notifications` | `page,pageSize,state=delivered|read` |
| GET | `/api/v1/notifications/unread-count` | `{count:number}` для колокольчика |
| POST | `/api/v1/notifications/read-all` | Прочитать доступные уведомления получателя |
| POST | `/api/v1/notifications/:id/read` | Прочитать одно |
| POST | `/api/v1/notifications/:id/snooze` | `{until:ISO}` |
| PATCH | `/api/v1/notifications/:id` | `{action:read}` либо `{action:snooze,until:ISO}` |
| GET/PUT | `/api/v1/notifications/preferences` | `{leadMinutes:number}` |

Все маршруты проходят существующие session/RBAC, CSRF и standby middleware. Получатель уведомления всегда берётся из сессии.

## Эксплуатация

`docker compose up -d worker` запускает `tsx src/worker/notifications-worker.ts` в том же образе, что и приложение, после успешного migrate-сервиса. Dockerfile уже копирует `/app/src` и production `node_modules`; `tsx` — production dependency. Воркеру не нужен браузер, файлы или внешний доступ. HTTP healthcheck образа для него отключён. `docker compose logs --tail=50 worker` показывает только технические события и количество доставленных напоминаний.

`NOTIFICATIONS_INTERVAL_MS` — интервал опроса, по умолчанию 15000, допустимый фактический диапазон 1000–60000 мс. `INSTANCE_ROLE=standby` полностью отключает создание и доставку; для смены роли перезапустите контейнер с новым окружением. Используется существующий operational contract экземпляра, дополнительного offline fencing нет.

Каждый tick: PostgreSQL transaction advisory lock `(241008,1)` → вычисление актуальной очереди → dismiss устаревших pending → `createMany(skipDuplicates)` с уникальным dedupKey → доставка всех наступивших событий. Курсора в памяти нет; рестарт догоняет пропущенные сроки. После изменения исходного срока или настроек pending актуализируются на следующем tick, до доставки. Snooze не меняет срок источника. Выполненные/отменённые источники отменяют pending. Повторная доставка уже delivered/read по тому же ключу не производится. SIGTERM/SIGINT прекращают цикл и закрывают пул.
