# Инженерные допущения реализации

Фиксируются решения по вопросам, которые ТЗ v1.6.1 допускает трактовать по-разному.
Формат: что было неоднозначно → решение → почему → что затрагивает.

## A-01. Видимость потребностей, обращений и показов риелтору
- **Неоднозначность:** ТЗ: «риелтор видит только своих клиентов» и «связанные с ними оперативные данные»; у ClientNeed/LeadRequest есть собственный `responsible_user_id`.
- **Решение:** риелтор видит ClientNeed/LeadRequest, если он ответственный за запись **или** за её клиента. Showing/CommercialOffer/NeedPropertyMatch — через доступ к потребности (или собственная ответственность).
- **Почему:** после передачи клиента руководителем обязательства риелтора не должны «исчезать» (ТЗ 40.1), но чужой клиент не раскрывается.
- **Затрагивает:** `src/modules/access/domain/scopes.ts`, все выборки, поиск, экспорт, выдачу файлов.

## A-02. Ответ на запрос недоступной записи
- **Решение:** для конкретной записи (чужой Client по ID, файл недоступной сущности) API возвращает `404 NOT_FOUND`, для функций роли (админка, архив, импорт) — `403 FORBIDDEN`.
- **Почему:** ТЗ 32.1 — внешний ответ не раскрывает сведений о недоступных объектах; 404 не подтверждает существование записи.
- **Затрагивает:** application-сервисы, `src/server/api-handler.ts`, authorization-тесты.

## A-03. Документы объекта недвижимости
- **Неоднозначность:** каталог объектов виден всем риелторам, но «доступ к связанным файлам» подчиняется правилу контактов собственника (ТЗ 17.2).
- **Решение:** фото объекта (`document_type_code=photo`) доступны всем, кто видит каталог; прочие документы объекта (правоустанавливающие, договоры) — только при доступе к контактам собственника (ответственный, grant, руководитель).
- **Почему:** такие документы обычно содержат ПДн собственника.
- **Затрагивает:** `documentScope()`, выдача файлов, поиск.

## A-04. Назначение ответственного за задачу
- **Решение:** руководитель назначает любого активного сотрудника; риелтор — себя, ответственного по потребности или руководителя (эскалация).
- **Почему:** ТЗ 32.1 — сервер не доверяет произвольному `user_id` из формы.

## A-05. «Task возврата» для paused
- **Решение:** любая незавершённая (planned/in_progress) Task, связанная с потребностью через `task_needs`. Отдельного типа «возврат» в codebook нет; UI формирует такую задачу с заголовком «Вернуться к потребности».
- **Затрагивает:** `src/modules/needs/domain/need-invariant.ts`.

## A-06. Просрочка
- **Решение:** задача просрочена, если она открыта и `due_at < now()` (а не «раньше начала текущих суток»). «Сегодня» — срок от текущего момента до конца локальных суток `APP_TIMEZONE`.

## A-07. Первичные учётные записи
- **Решение:** seed создаёт руководителя и двух риелторов с паролями из `SEED_*_PASSWORD`, которые генерирует `scripts/bootstrap.sh`; при первом входе требуется смена пароля. Существующие пользователи seed не изменяет.

## A-08. Юридические субъекты
- **Решение:** seed создаёт «ООО «Магазин недвижимости»» и ИП с наименованием-заглушкой; реальные реквизиты вносит руководитель (Администрирование → Юрлица). Реквизиты ИП являются ПДн и в репозиторий не попадают.

## A-09. Сервис migrate выполняет и seed
- **Решение:** одноразовый `migrate` выполняет `prisma migrate deploy && prisma db seed`; seed идемпотентен.
- **Почему:** штатная установка должна сводиться к `bootstrap.sh && deploy.sh` (ТЗ 36.6).

## A-10. Типы операций
- **Решение:** операция потребности (со стороны клиента): `buy`, `rent`, `sell`, `lease_out`; операция объекта: `sale`, `rent`. Подбор: `buy → sale`, `rent → rent`. Это бизнес-справочники, предприятие может их расширять.

## A-11. Район
- **Решение:** `district` — свободный текст с подсказками из уже введённых значений, а не справочник: реальный перечень районов предприятия в ТЗ не задан.

## A-12. Учётные данные контейнеров
- **Решение:** контейнеры `app`, `migrate`, `backup` работают от uid/gid владельца каталогов `data/` и `backups/` (`APP_UID`/`APP_GID` задаёт bootstrap; по умолчанию 1000).
- **Почему:** bind mount `./data/files` (ТЗ 36.2) должен быть доступен на запись без ручных chmod.

## A-13. Единица площади участка
- **Решение:** `land_area` (объект) и `land_area_min/max` (потребность) — в сотках; площадь помещений и зданий — в м².
- **Почему:** так площадь участка указывается в практике предприятия; подбор сравнивает значения в одной единице.

## A-14. Импорт «Наличие договора: да» без даты
- **Неоднозначность:** в таблице анализа договоров есть признак наличия договора, но нет даты подписания, а `signed` требует `signed_at` (ТЗ 29.14).
- **Решение:** создаётся Agreement в статусе `draft` с требуемым действием «Уточнить дату подписания и реквизиты»; «нет» → `no_agreement` с причиной. Задачи из «Что нужно исправить» создаются только при явном выборе в мастере импорта (ТЗ 38.6).

## A-15. Импорт текущих клиентов
- **Решение:** «Координаты» считаются телефоном/e-mail только при явной опции мастера; иначе остаются в `lead_requests.raw_contact`. Для активной импортированной потребности создаётся задача «Актуализировать запрос клиента (импорт)» — инвариант next action соблюдается и для исторических данных. Вероятные дубли по телефону пропускаются (без auto-merge), операция «универсал» не создаёт потребность.

## A-16. Content-Security-Policy
- **Решение:** в production действует CSP с `script-src 'self' 'unsafe-inline'` (Next.js App Router использует inline-скрипты гидратации); `frame-ancestors 'none'`, `X-Frame-Options: DENY`, `nosniff`. В dev-режиме CSP отключена (React/HMR используют eval). Переход на nonce-CSP — в backlog.

## A-17. Ручной backup из интерфейса
- **Решение:** кнопка «Создать backup сейчас» запускает тот же скрипт `ops/backup/scripts/backup.sh` внутри контейнера приложения (в образе есть PostgreSQL 18 client и zstd), статус пишется в `backup_runs`. Off-site репликация и восстановление выполняются только скриптами ops-контейнера, где доступны секреты rclone; приложению секреты не передаются.

## A-18. Ответ на неверные учётные данные
- **Решение:** неверный логин/пароль и деактивированная учётная запись → `401 INVALID_CREDENTIALS` с одинаковым текстом; отсутствие/истечение сессии → `401 UNAUTHENTICATED` (клиент перенаправляет на вход).


## P1-А v2.4.1 (05.11.2026)

- Перспективность выражена стабильными resultCode `new_need` / `linked_existing_need`, без изменения схемы. `processed` сохраняет открытость работы, пока потребность active/paused; актуальное действие имеет открытый статус и непросроченный срок. Отказ/спам/разовая услуга фиксируют причину в summary.
- `no_match` оставлен в codebook для чтения истории, но новые операции закрытия потребности с этой причиной запрещены (§2 v2.4.1).
- Связь новой редакции КП хранится в существующем metadata-поле promptTemplateVersion как `revision-of:<uuid>`; копируются исторические снимки. Фото при выгрузке выбираются из текущих разрешённых файлов. Схема не менялась.
- Текущие активные состояния/просрочки не ограничиваются датой создания. Фильтр источника определяет когорту обращений периода и связанные записи; детализация использует те же cohorts. При пустом знаменателе доля 100% сопровождается явным «0 из 0».
- Карточка объекта для печати использует явно выбранное legalEntityId либо первое активное юрлицо; секретные сведения и контакты собственника в выгрузку не включаются.
- Нет локально проверенного PDF-конвертера: реализованы DOCX/HTML, PDF не заявляется.

## Desktop SQLite, этап 2 (v3.2.1 §4)

- История SQLite-миграций должна работать офлайн без Prisma CLI/schema engine в host PATH. Используется исполнитель зафиксированных migration.sql с SHA-256 и совместимой `_prisma_migrations`; совместимость с Prisma migrate deploy проверяется integration-тестом.
- PG→SQLite читает согласованный READ ONLY REPEATABLE READ snapshot; для согласованности файлов оператор останавливает writers до переноса. Входные PG/storage не меняются. Target и его storage обязаны быть новыми. Полный FK check сильнее выборочной проверки связей; отдельно проверяются сценарные ID/API/финансы/документы.
- AI-анализ сохраняет оплаченную группу независимо от следующей группы. В SQLite lock scope — внутрипроцессная очередь файла; budget read/check/reserve остаётся BEGIN IMMEDIATE transaction. Server сохраняет advisory transaction scope и независимые коммиты.
- Runtime init --initialize не создаёт пользователя: пароль задаётся в мастере. Отдельный --setup-stdin предназначен для локальной автоматизации без пароля в argv/stdout. `local-secrets.json` защищает ACL supervisor; секреты не заменяют login/CSRF/Origin.
- Из-за Windows subprocess-тестов в unit-проекте установлен testTimeout=15 секунд (ранее 5); проверки confidentiality не менялись. Функциональные integration/authorization assertions и таймауты сохранены.
