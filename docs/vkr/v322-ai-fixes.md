# Поиск v3.2.2: AI-01–03 и отдельное AI-ранжирование

Дата: 2026-11-08. Ветка: feature/ux-search-v3.2.2-search. Область: автоматические REPLAY/fake тесты, без платных AI-вызовов.

## Изменения

- AI-01: сохранение условий распознаёт «до 80 000», «от 50 тыс», «80к», «за 80 000 в месяц», «до 7 млн». REPLAY-ответ модели проходит decode → preservation → validation. Точный запрос аренды 50–100 м² с priceTo=80000 дополнительно проходит preview и confirm. Покрыты м2/м²/словесная площадь, этажи, «снять»/«сдам», сохранение несвязанных условий и периода аренды при уточнении только бюджета.
- AI-02: `ExternalListing.priceUnit` nullable в PG и SQLite. Неизвестный период сохраняется как NULL, UI показывает «период не указан», AI получает явное предупреждение «Период цены неизвестен — цены несопоставимы до проверки». Правило сравнения исключает неизвестные периоды, в том числе ошибочный legacy total при source snapshot null. [ADR 0011](../adr/0011-unknown-listing-price-period.md) объясняет миграции и backfill. Обновление заполненной SQLite сохраняет историю, FK и все 11 явных индексов.
- score=0 был ожидаемым результатом отсутствия preferredFeatures: оценка считает долю подтверждённых предпочтений. Это проверено тестом 0 без предпочтений / 100 при подтверждённой парковке. Название сортировки теперь «Совпадение предпочтений (без ИИ)».
- Добавлены кнопка «Ранжировать выбранные с ИИ» и POST `/api/v1/property-search/analysis/rank`: 2–10 выбранных объявлений, лимит руководителя, тот же offer_text budget/ledger и постоянный AiAnalysisCache. Ключ включает модель, фильтры и критерии; перестановка ID не сбрасывает кэш, изменение фактов сбрасывает. Параллельные запросы не оплачивают одно и то же дважды.
- Ответ модели содержит только упорядоченные ID и ссылки на критерии. Сервер до успешного settlement отклоняет неизвестные/повторные/пропущенные ID, отсутствующие критерии и лишние поля. Краткие русские основания формируются из результатов серверной проверки; модель не может добавить новый факт. Рекомендация визуально отделена от фактов, опубликованные данные не меняются.
- AI-03: реальный клиент Yandex с официальным разрешённым URL и синтетическими реквизитами получает injected fetch reject или abort/timeout. Сетевых обращений нет. AI-действие возвращает контролируемое AI_CALL_FAILED с понятным сообщением; ручной поиск без AI сохраняет результат, `/api/health/ready` отвечает 200 после возврата AI_ENABLED=true. Allowlist не менялся.

## AI-RANK-LIVE-01 — диагностика и исправление, 2026-11-08

На `aliceai-llm-flash/latest` напрямую вызван тот же `SearchAi.rankListings` → `YandexResponsesClient`, без приложения и БД, на трёх синтетических объявлениях. Первый простой набор прошёл; расширенный набор воспроизвёл `AI_INVALID_JSON_RESULT`: модель вернула **5 reasonCriteria**, тогда как Zod допускает 1–3. JSON был единственным, полным, без markdown; 174 выходных токена при лимите 1800. В отправленной провайдеру схеме отсутствовал `maxItems`. Это доказанная причина воспроизведённого отказа; сырой ответ исходного исторического прогона не сохранён, его точную идентичность утверждать нельзя.

Исправление: strict `text.format.json_schema` теперь задаёт 1–3 основания, точное число объявлений, enum разрешённых ID/критериев; prompt содержит явную структуру и требование выбрать только важнейшие основания. [Контракт Responses API Yandex](https://aistudio.yandex.ru/en/docs/ai-studio/api/Responses/createResponse) использует `text.format`, а не chat `response_format`. Серверная проверка схемы, уникальности, полноты и принадлежности критериев конкретному объявлению сохранена. Размер output резервируется до отправки: max(config, 512 + 192 × число объявлений), для трёх при config=1800 остаётся 1800. Существующее извлечение единственного JSON с учётом строк/экранирования сохранено и покрыто тестами: markdown, пояснения и BOM допустимы, конкурирующие/обрезанные объекты отклоняются. Бизнес-данные не исправляются и не обрезаются. Ошибка формата теперь объясняет, что результат не применён, автоматического повтора нет, новый запрос может быть платным.

REPLAY: `tests/unit/ai/fixtures/ranking-live-synthetic.txt` — точный синтетический LIVE-ответ с пятью основаниями (ожидаемо отклоняется); `ranking-live-fixed-synthetic.txt` — принятый финальный LIVE-ответ. Тесты проверяют provider schema против записанного отказа, 0/4/5 оснований, дубли, лишние/неизвестные ID/поля/критерии, критерий чужого объявления, 2/10 объявлений, резерв output, settlement и отсутствие повторного dispatch. Фикстуры не содержат секретов или реальных объявлений.

| LIVE | Input/output токены | Расчёт по seed-тарифу, ₽ | Итог |

| Простой набор, до исправления | 471/159 | 0.078900 | PASS |

Итого **3 платных вызова, 1806/497 токенов, 0.280000 ₽** по существующему seed-тарифу 100/200 ₽ за миллион токенов; это расчёт диагностики, не сверка счёта Yandex. Записи CRM AI-журнала не создавались. Предварительный sandbox-запуск не дошёл до провайдера (DNS ENOTFOUND); его консервативный process-local reserve не является фактическим расходом. Финальный запрос принят с той же схемой, prompt и max_output_tokens=1800, что применяются исправленным кодом для этого набора.

## Финальное ревью — 08.11.2026, только fake/REPLAY

1. `AgreementForm.dirty` теперь учитывает отдельные состояния ответственного и напоминания. Unit-проверки рендера контролируют аргумент настоящего места вызова `useUnsavedChangesWarning`: исходная форма, смена только ответственного, смена/отключение напоминания, успешное сохранение. Сдвоенный import в результатах поиска разделён.
2. Кэш рекомендаций ранжирования переведён на `listing-ranking-v2`: ключ включает ID и роль актора, `needId`, модель, фильтры и отсортированные факты. Старые общие ключи не читаются. Повтор/перестановка ID у одного пользователя сохраняют кэш; второй пользователь получает собственный результат и собственную запись расходов.
3. Сравнение существующих политик: `compareAnalysisListings` проверяет `selected()` и вызывает `withP2Ai` без постоянного кэша; `analyzeListingBatch` разделяет по тексту/критериям/модели только публичные доказательства описания и проверяет `selected()` до кэша. Ранжирование намеренно изолировано строже. Каталог внешних объявлений общий; наличие каждого выбранного объявления и текущие права на Need проверяются до любого cache hit. Integration проверяет двух акторов, повтор каждого, чужую Need, отзыв доступа у создателя кэша и исчезновение одного объявления при сохранённом кэше.
4. Платный вызов под advisory lock **оставлен намеренно**: это существующий паттерн `analyzeListingBatch` → `independentCommitScope` → lock → lookup → `withListingAi` → `withP2Ai`. Сам `withP2Ai` не открывает транзакцию и не задаёт политику дедупликации. В PG транзакция удерживает только блокировку кэш-ключа (timeout 180 секунд), а ledger и успешный оплаченный кэш сохраняются независимо через `db`; в SQLite тот же scope сериализует работу через `serializeSqliteWork`. Перенос вызова за пределы lock допустил бы повторную оплату параллельных промахов. Тест одновременных запросов подтверждает один dispatch на обеих БД; ошибка провайдера не оставляет ложного кэша. Длительное удержание соединения ограничено timeout; это осознанный компромисс существующего решения.

5. Замечание о росте ложных пометок `normalization.ts` **не подтверждено на корпусе 49**: отдельный REPLAY-тест подключает именно `deduplicateListings` к размеченным парам, поскольку штатный quality gate использует `compareListings`. Получено **TP=3, FP=0, FN=0, TN=2** на пяти размеченных парах; три неизвестные пары исключены из оценки. Отдельные регрессии подтверждают отсутствие пометки у разных известных номеров дома/корпусов и сохранение обеих карточек. Ужесточение не внесено: на этом корпусе оно не устраняет ложных положительных пометок и может потерять известный street-only кандидат D03. Это ограниченное доказательство по размеченному корпусу, а не гарантия для всех адресов.

Фактические проверки этого ревью: unit поиска/AI/формы/UX — **47 файлов, 1236 PASS**; `listing-analysis-v31.test.ts` — **33 PASS PG crm_test_e**, **33 PASS SQLite**; `tsc --noEmit` и ESLint изменённых TS/TSX — PASS. Платный AI, .env, private-data и XLSX не читались/не вызывались.
