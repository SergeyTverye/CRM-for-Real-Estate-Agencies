## Реализация и границы

- Браузер передаёт только проверенный тип контекста и UUID, полученный из маршрута. `/new` не считается карточкой. Списки не сериализуются.
- `application/screen-context.ts` — серверный whitelist assembler, выборка через Prisma select. Имена, контакты, владельцы, пароли/сессии, реквизиты, примечания карточек и содержимое документов не выбираются. Для задачи заголовок и описание изолированы в untrusted_data и проходят существующий серверный privacy-фильтр с известными идентичностями до отправки провайдеру. Тексты пользовательского запроса и инструментов проходят существующий privacy-фильтр.
- Сводка собирается на каждом сообщении заново. Доступ проверяется при создании, чтении, отправке, после ответа и при подтверждении черновика. Задача с любой чужой связью не даёт AI-контекст. Сделка/договор дополнительно требуют доступности всех связанных клиентов, даже если карточка доступна по ответственному.
- История ссылок на сделки/договоры проверяется той же усиленной политикой. Подписи остаются на сервере; внешняя модель получает UUID и структурные факты.
- В панели виден контекст выбранного диалога, вопросы зависят от экрана. При смене страницы появляется указание создать новый диалог: старый контекст не меняется скрыто.
- «Создать задачу» открывает существующую форму с clientId/needId/dealId/agreementId. Проверка связей, срок и сохранение остаются за пользователем. AI-черновик задачи/КП не выполняется до кнопки подтверждения, идемпотентность подтверждения сохранена.
- Версия инструкции `screen-context-v2`; конкретные следующие действия, уточняющие вопросы, риски сроков, черновик сообщения. Модель предупреждена, что bounded sample не является полным списком. Юридическое заключение и автоматическая отправка сообщений отсутствуют.
- Для отчётов используется явно подписанный период по умолчанию, а не фильтры текущего URL. Свободные комментарии сознательно не передаются: помощник знает тип/результат коммуникации, но не её полный текст. Порядок «Сегодня» — ближайший срок; приоритет передаётся отдельно.
- Необходима миграция CHECK контекста чата `20261109003000_ai_screen_context` для PG/SQLite; новых бизнес-таблиц нет. SQLite rebuild сохраняет сессии, сообщения, действия, FK и индексы, проверяется с транзакцией и без неё.
- Структурные суммы/даты/коды сохраняются точно; фильтр применяется только к untrusted_data. Regression: бюджет 50 000 000 не превращается в телефонную маску.
- Предварительная стоимость входа рассчитывается по UTF-8 размеру реально отправляемого запроса с запасом, вместо постоянных 24000 токенов. Gate, лимиты и окончательное списание по provider usage не обходятся.

## Разрешение LIVE

Первый запуск LIVE автоматически отклонён контролем разрешений: он запросил дополнительное подтверждение внешнего Yandex destination, payload и расходования средств, несмотря на прямое поручение LIVE в файле задачи. Отказ не обходился: выполнена безопасная локальная DEMO-альтернатива (AI_ENABLED=false, ключ провайдера очищен, API interception). Сформирован обезличенный payload и доказательства синтетического происхождения для повторной проверки разрешения. После предоставления явного поручения из файла задачи, безопасных payload и результатов тестов повторный запрос одобрен автоматическим контролем. LIVE выполняется отдельным runner; его фактические результаты приведены ниже. DEMO не объявляется LIVE.


## LIVE наблюдения и исправления

Первый реальный прогон: пять экранов, 5 вызовов, 0.863600 ₽ (точность внутреннего журнала micro-RUB). Контекст использован: модель назвала параметры потребности, сроки задач, незавершённые пункты сделки; ни одной бизнес-мутации не выполнено. На «Сегодня» руководителя собственных открытых задач нет — ответ корректно отразил пустой личный план.

Найденные ограничения модели v1: упоминала внутренние имена инструментов; выводила сырые коды чек-листа; могла предполагать причины будущего риска без фактов. Выпущена инструкция v2: обычные действия вместо API, факты отдельно от предположений, русские системные подписи чек-листа. Первые ответы сохранены для сравнения, а не выданы за идеальный результат. Для проверки v2 используются только оставшиеся три вызова из исходного максимума восьми и тот же финансовый потолок; журнал и baseline расходов не сбрасываются.


Дополнительная регрессия LIVE: общий privacy-фильтр ошибочно маскировал «Не» и обычные слова начала вопроса, меняя смысл запроса. Исправлено: отрицания и ограниченный словарь CRM-команд сохраняются, имена/контакты/секреты по-прежнему удаляются. Проверено unit-тестом с отрицанием и секретами в одной строке. Это изменение входит в `2549991`.
