# Рабочая книга объектов и обращений — профиль v2

Реализован независимый v2-путь поверх существующих ImportJob/ImportRowResult, Prisma и StorageAdapter. Старые v1-профили и маршруты сохранены. PostgreSQL-схема и миграции не изменялись; новых npm-пакетов нет (использованы установленные exceljs 4.4.0, fflate, Zod).

## Конфиденциальность и локальный координатор

Разработчик/агент не открывает реальную книгу и производные. Все проверки этого изменения выполнены на генераторе синтетики. DT-22 и DT-23 для реального файла остаются PARTIAL до доверенной локальной приёмки; синтетические результаты не заменяют её.

Только доверенный координатор запускает:

```powershell
node scripts/private-import/build-profile.mjs <локальный-xlsx> --out private-data/enterprise-profile.json
```

Скрипт сохраняет нормализованные заголовки исключительно в указанный JSON внутри private-data. stdout: классы листов, число строк, unresolved по числовым координатам; stderr: только безопасный код. Ошибки библиотеки не печатаются. Профиль и исходная книга не передаются модели, не включаются в Git/CI. Windows ACL каталога private-data должен настроить локальный оператор; POSIX mode сам по себе не устанавливает Windows ACL.

## Профиль

`import-profiles/enterprise_workbook_v2.schema.json` — JSON Schema, построенная из серверного Zod-контракта; `enterprise_workbook_v2.synthetic.json` — только вымышленные заголовки. Перегенерация обоих: `node scripts/private-import/update-synthetic-profile.mjs` (читает только именованную синтетическую фикстуру).

- `version: 2`, `code: enterprise_workbook_v2`, `sheets[]`.
- Выбор листа: `index` (1-based) или `namePattern` (регистронезависимое выражение); при совпадении нескольких конфигураций применяется первая. Шаблоны намеренно ограничены: без групп, фигурных скобок, плюса и обратных слешей. Поддерживаются простые альтернативы `аренд|сда` и шаблоны имён.
- `target`: property / client_request_need / historical_deal_archive / ignore. Автопостроение предлагает первые три листа как объекты, четвёртый как обращения, пятый как legacy-архив, шестой игнорирует. Это предложение, требующее проверки руководителем, а не утверждение о семантике конкретной книги.
- `headerRow: auto` обнаруживает каждую строку с минимум тремя известными заголовками; поддерживает повторные блоки. Можно указать конкретную строку. Словарь расширяется через `columns`.
- `columns`: нормализованный заголовок → поле CRM; `null`/отсутствующий ключ → unresolved и запрет commit; `ignore` → явное подтверждение пропуска. Две колонки e-mail объединяются; при экспорте контакты записываются в первую соответствующую колонку.
- `sections`: правило `{pattern,propertyType?,operationType?,district?}` для жирных строк с 1–2 текстовыми ячейками. Контекст действует до следующего заголовка/правила. Атрибуты строки имеют приоритет для операции/района.
- `hiddenRows: skip` либо `archive`. При archive объекты архивируются с archivedAt. Для обращений/истории факт скрытия остаётся в warningCodes; автоматически архивировать связанного Client небезопасно.
- `defaults`: propertyType, operationType, district, priceUnit. Аренда с ценой без явной единицы отклоняется. Единицы: rub_total / rub_month / rub_m2 / rub_m2_month / rub_year / rub_m2_year. Единица хранится в расширяемых attributesJsonb объекта; не меняет существующий контракт цены.
- `statusMap`: нормализованная метка → draft/active/paused/closed/archived для Property; `purposeMap`: назначение → код commercial_purpose; `sourceMap`: источник → активный код lead_source; `responsibleMap`: текст → UUID действующего сотрудника. Неопределённые исходные метки/ответственные/источники дают REQUIRES_MANUAL_REVIEW, используются безопасные active/other/руководитель; требуется подтверждение предупреждений. Статусы потребности из неоднозначных меток автоматически не выводятся.
- Собственник создаётся/связывается только при паре имя+нормализованный телефон. Неоднозначная пара требует ручной проверки; автослияния клиентов по ФИО нет. Чувствительные колонки (паспорт, выдан, регистрация, дата рождения) исключаются даже при попытке перепривязки в профиле.

Числа обрабатываются десятичными строками без умножения float (руб./тыс./млн/м2/м²), этаж `1/5 эт.` разбирается в два поля. Поддерживаются Excel Date, числовые serial (включая date1904), текстовые даты, несколько телефонов/e-mail. Формулы не вычисляются: используется только существующий cache; отсутствие результата приводит к пустому полю/ошибке обязательного ключа. Макросы и внешние связи workbook отклоняются. Ограничения: 30 МБ compressed, 100 МБ expanded, 32 МБ на ZIP entry, 30 листов, 50 000 строк/лист, 200 колонок.

## API и мастер

Все маршруты — действующая сессия руководителя, общая Origin/standby-защита; риелтору отказ до чтения закрытых данных.

| Метод | Путь | Назначение |
|---|---|---|
| POST | /api/v1/import/enterprise | multipart file + необязательная строка profile(JSON); загрузка и dry-run |
| GET | /api/v1/import/enterprise/{id} | profile, checksumRepeated, mappingVersion, агрегаты, координаты и коды строк |
| PATCH | /api/v1/import/enterprise/{id} | профиль v2; повторная проверка и замена результатов только до commit |
| POST | /api/v1/import/enterprise/{id} | {confirmed:true,acceptWarnings:true,expectedMappingVersion}; атомарный commit |
| GET | /api/v1/import/enterprise/{id}/export | XLSX; X-Import-Compatibility с агрегатами несовместимостей |

Раздел `/import`: отдельный мастер рабочей книги, выбор авто/локального JSON-профиля, отчёт по листам/разделам и координатам, редактирование JSON-mapping, подтверждения, commit, экспорт и видимый отчёт совместимости. История `/import/{id}` повторно открывает тот же мастер. Нет вывода фрагментов коммерческих строк в отчёте. Незавершённое редактирование защищено beforeunload.

Источник хранится по непрозрачному StorageAdapter key `private-import/...`, вне public; имя в журнале обезличено. Это одновременно сохранённый шаблон. Срок хранения — до административного удаления/политики retention хранилища; автоматическая очистка v1 staging его не удаляет. Backup должен включать всё файловое хранилище. Права ОС/резервное копирование каталога — эксплуатационная обязанность.

Dry-run записывает только ImportJob/ImportRowResult без значений исходных строк; mapping содержит заголовки и доступен только руководителю. Значимые бизнес-значения попадают только в operational entities при commit. История сделок импортируется в HistoricalDealArchive: номер/адрес/площадь/цена/договор/комиссия, без создания недостоверного operational Deal/DealCommission.

## Атомарность и дубли

Ключ строки — SHA-256 от порядкового листа, target и нормализованных ключевых полей; checksum/номер строки в нём не участвуют. Для объектов это адрес+площадь+операция; для обращения — отсортированные контакты+дата; для архива дополнительно исходный №. Отдельно сохраняются checksum файла и координаты исходной строки. Перестановка листов меняет ключ, но дополнительные бизнес-проверки объектов/контактов продолжают защищать от дублей.

Перед записью проверяются прошлые импортированные ключи, объекты по адресу+площади+операции, контакты и дубли внутри книги. Вероятные дубли пропускаются, автоматического merge нет. Commit одной книги атомарен: claim, все допустимые бизнес-записи, квитанции и аудит — одна транзакция. Недопустимые строки пропускаются; неожиданный сбой откатывает весь commit, job остаётся dry_run_ready. Повторный completed commit возвращает прежний результат. Версия mapping защищает от изменения профиля между проверкой и подтверждением.

Конкурирующие v2-задания сериализуются записью одной стабильной строки User руководителя; PG raw SQL отсутствует. Это работает через Prisma и доступно SQLite-агенту. Конкурентный v1 и v2 не сериализуются этой блокировкой: не запускайте разные поколения импорта одновременно. Массовый импорт ограничен общим таймаутом transaction (30 с); превышение безопасно откатывается и требует меньшего входного набора.

## Обратный Excel и границы совместимости

Экспорт заполняет копию сохранённого шаблона актуальными CRM-записями, созданными этим заданием (по квитанциям). Новые посторонние записи CRM автоматически не добавляются; для них остаётся общий экспорт CRM. Сохраняются листы, ширины, стили, фильтры, закрепления, подзаголовки, четыре defined names и поддержанные ExcelJS изображения. Исходный файл не изменяется.

Перед заполнением очищаются все строки данных, включая отклонённые/скрытые/служебные листы; колонки без источника остаются пустыми. Формулы данных заменяются значениями CRM/пустотой и учитываются FORMULA_CLEARED; неизвестные типы не исполняются. Ссылки в описании сохраняются только из актуального Property.sourceUrl; ссылки отклонённых строк очищаются и учитываются HYPERLINK_CLEARED. Не гарантируется бинарное тождество, полный перенос неподдерживаемых drawing/custom Excel extensions или формул. Отчёт: UNSUPPORTED_COLUMN / UNSUPPORTED_FIELD / FORMULA_CLEARED / NUMBER_AS_TEXT / IMAGE_PRESERVED / HYPERLINK_PRESERVED / HYPERLINK_CLEARED. Повторный импорт экспорта подтверждён синтетическим PG-тестом без прироста объектов/клиентов/истории.

## Воспроизводимая проверка

```powershell
node scripts/private-import/make-enterprise-synthetic.mjs
node scripts/private-import/update-synthetic-profile.mjs
$env:TEST_DATABASE_URL='postgresql://crm:crm_test_password@127.0.0.1:55432/crm_test_d'
npx vitest run --project unit --project integration tests/unit/enterprise-workbook.test.ts tests/integration/enterprise-workbook.test.ts tests/integration/import.test.ts
npx tsc --noEmit
```

Фикстура содержит только вымышленные записи и example.invalid: 6 видимых листов, 4 имени, два блока листа 5, merge на листе 5, 42 скрытые строки каждого каталога, 15 картинок/31 ссылку листа 2, фильтры/закрепления, строки-числа, длинные описания, даты/телефоны/две колонки e-mail, служебный 5×6 блок. Генератор никогда не обращается к реальной книге.

Проверки: unit — структура/нормализация/политика/повреждение; PostgreSQL и SQLite — dry-run, unresolved/remap, commit/repeat/checksum, rollback/retry, отказ половины строк, экспорт/повтор импорта/стили/ширины/фильтры/имена/изображения, конкурентные задания, архив, source/responsible/status mapping, закрытый журнал и все операции для двух риелторов.

## Доверенный локальный проверочный контур (DT-22/23)

Запускает только локальный оператор; агент и CI используют исключительно синтетическую фикстуру:

```powershell
node --import tsx scripts/private-import/verify-workbook.ts <xlsx> --profile <json> --backend sqlite
node --import tsx scripts/private-import/verify-workbook.ts <xlsx> --profile <json> --backend pg
```

Профиль должен быть согласованным v2: unresolved не подтверждаются автоматически. Файл `enterprise_workbook_v2.synthetic.json` намеренно содержит unresolved; тест создаёт отдельный синтетический профиль с явным `ignore`. Ответственные из профиля должны существовать в изолированном контуре: реальные UUID рабочей БД автоматически не переносятся и не подменяются. Для локального приёмочного профиля используйте безопасный fallback руководителя, оставляя предупреждения для проверки. OS ACL для private-data настраивает оператор до запуска.

PG принимает только loopback `127.0.0.1:55432`, реквизиты — TEST_DATABASE_URL, целевая БД всегда `crm_private_verify`. Этот единственный временный database пересоздаётся и удаляется; advisory lock запрещает два одновременных проверочных запуска. Нужны CREATE/DROP DATABASE. Рабочая БД и crm_test_d не используются скриптом. SQLite — отдельный временный файл. Все файлы, включая staging, шаблон и экспорт, находятся в уникальном каталоге private-data/verify-tmp/run-*; штатный выход и обработанные ошибки удаляют каталог. Принудительное завершение процесса/потеря питания требуют локальной очистки оператором; следующий PG-запуск пересоздаёт только свою БД.

Скрипт применяет миграции, создаёт синтетические роли/справочники, проверяет dry-run без бизнес-записей, ошибки/дубли, атомарный rollback и retry через временный DB trigger после половины пригодных строк, commit/repeat, экспорт/reimport, значения ключей/дат/сумм и структуру, RBAC чужого клиента/потребности/архива и закрытого журнала. Для fault-injection нужны минимум две пригодные уникальные строки. Завершение с кодом 0 означает успешный контур; ненулевой код требует проверки агрегатов. Ошибки строк/совместимости сами по себе отображаются отдельно и не означают, что вся исходная книга принята без исключений.

stdout — один JSON: только числовые листья, фиксированные ключи, номера листов и unresolved-координаты. stderr и диагностический вывод зависимостей подавляются, вывод мигратора захватывается и отбрасывается. Имена листов, заголовки, значения, paths, UUID, hashes, сообщения исключений не выводятся. SHA-256 исходника сравнивается до/после, наружу только source_unchanged=1/0. Сравнение чувствительных значений выполняется в памяти. Несовпадения экспорта остаются агрегатами matched/mismatched; неподдержанные элементы — отдельные счётчики compatibility. Отчёт не даёт гарантии бинарного тождества.

Автотест `tests/integration/private-workbook-verifier.test.ts` запускается в проектах integration и integration-sqlite; проверяет оба CLI backend, отсутствие строковых листьев/синтетических текстов, stderr, rollback/retry, 0 новых при повторе, SHA и cleanup. Сравнение намеренно повреждённого экспорта — tests/unit/private-workbook-comparison.test.ts.

Фактические результаты и остающиеся ограничения typecheck/UI см. последнюю запись `docs/import/enterprise-workbook-verification.md`.
