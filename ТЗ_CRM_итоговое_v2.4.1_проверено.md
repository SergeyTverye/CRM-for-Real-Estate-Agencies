## 1. Цель, границы и приоритеты

CRM предназначена для руководителя и двух риелторов небольшого агентства коммерческой недвижимости. Она должна сохранять историю клиентов, не терять перспективные обращения, ускорять подбор объектов и подготовку КП, контролировать сделки и последующие контакты. Отличительная возможность продукта — **единый поиск объектов через собственную базу, скрапер и Yandex AI с переходом к реальной работе по клиенту**.

| Приоритет | Обязательный результат |
|---|---|
| **P0, до пилота на реальных данных** | Устранить утечки персональных данных во всех API, проверить права на файлы, восстановление из резервной копии и целостность данных |
| **P1-А, основной рабочий контур** | Контроль следующего контакта, галерея объектов, базовые документы и КП, календарь и уведомления в CRM, отчёты и исправление инвариантов |
| **P1-Б, интеллектуальное расширение для ВКР** | Интеграция скрапера и Yandex AI, анализ объявлений, закладки, подборки клиентов, резервный веб-поиск, управление лимитами |
| **Обязательная приёмка P1** | Автотесты, сквозные сценарии, обновлённая документация, демонстрационные данные, скриншоты и материалы ВКР |
| **P2, после P1** | Фирменные шаблоны после получения образцов, плановый автопоиск, дополнительные источники и второстепенные улучшения |
| **P3, дальнейшее развитие** | MAX-бот, внешние уведомления, телефония, внешние календари, ЭДО и автоматическая публикация рекламы |

P1-А и P1-Б можно разрабатывать параллельно, но исправления P0 должны предшествовать работе с реальными клиентскими данными. Для защиты допускается демонстрация отдельных недоступных внешних источников на заранее записанных ответах с обозначением режима тестирования. Такой прогон нельзя выдавать за успешный живой сбор.

Сохранить Next.js 16, React 19, TypeScript, Prisma 7, PostgreSQL, Docker и модульный монолит. Повторно использовать существующие `Client`, `ClientNeed`, `LeadRequest`, `Property`, `NeedPropertyMatch`, `Task`, `Showing`, `Deal`, `CommercialOffer`, `Document`, StorageAdapter, RBAC и журнал аудита. Не создавать параллельные базы клиентов и задач.

## 2. Обращения, клиенты и постсделочные задачи (P1-А)

**Сквозной процесс:** обращение → клиент/потребность → следующий контакт → подбор → предложение/КП → показ → сделка → документы → повторный контакт.

В быстрой регистрации обращения фиксировать источник, результат, ответственного и краткое содержание. Для **перспективного обращения** (клиент заинтересован в подборе и работа продолжается) требовать следующую задачу с ответственным и сроком. Отсутствие подходящих объектов не закрывает потребность. Отказ, спам и разовую услугу можно завершить с причиной без лишней задачи. Использовать существующие статусы и проверки там, где они подходят.

На `/today` и для руководителя показывать очередь перспективных обращений без действующего следующего действия и просроченные контакты с переходом к исходным записям. Сначала проверять уже существующие списки, поля и задачи, чтобы не дублировать логику. Определить показатель «доля перспективных обращений с назначенным действием» как отношение числа открытых перспективных обращений с актуальной задачей к числу всех открытых перспективных обращений за выбранный срез. Отдельно учитывать долю выполненных в срок контактов по фактической дате завершения задачи.

Карточка клиента объединяет доступные пользователю обращения, потребности, коммуникации, показы, КП, сделки и задачи. При повторном обращении сохраняется прежняя история, создаётся новая потребность при необходимости. Дубли и закрепление клиентов за сотрудниками обрабатывают существующие сервисы.

При закрытии сделки предложить редактируемый **набор постсделочных задач**: сверка расчётов, контроль сроков договоров/допсоглашений, продление аренды, повторный контакт, страхование или декларация при применимости. Сотрудник выбирает пункты, исполнителей и сроки. Задачи сохраняются через `Task` со связями с клиентом, сделкой и объектом. Применимость отдельных юридических действий определяет пользователь.

## 3. UI/UX вкладки «Поиск объектов» (P1-Б)

Добавить `/property-search` как отдельный раздел. Глобальный поиск внутри CRM сохранить. Открывать вкладку самостоятельно или из потребности клиента с предварительно выбранным `ClientNeed`. **Новосибирск — город по умолчанию**, в отдельном запросе разрешён другой город.

Экран содержит текстовое поле на русском языке, кнопку «Разобрать с ИИ», редактируемую панель фильтров, кнопку «Искать», статусы источников, переключение карточки/таблица, вкладки «Совпадения», «Требуют проверки», «Исключены», «Закладки», а также «Мои поиски». В карточке результата показывать источник, URL, дату получения, адрес, цену, площадь, этаж, фото при допустимом использовании и доказательства совпадения. Доступные действия: **«В закладки», «В подборку клиента», «Уточнить», «В каталог CRM», «Предложить клиенту», «В КП»**.

ИИ извлекает параметры из свободного запроса. Перед платным поиском риелтор может исправить распознанные условия и подтвердить запуск. Последующие фразы («добавь витрину», «исключи цоколь») изменяют предлагаемые фильтры. Когда смысл критического условия неясен, запросить уточнение. Без ИИ работает ручная форма фильтров.

### 3.1. Правила поиска

| Группа | Правило |
|---|---|
| Операция | Продажа или аренда, с явной единицей цены для аренды |
| Назначение | Нежилое. Торговля, ПСН/универсальное, офис, производство, склад, свободное назначение. Выбранные назначения объединяются по **ИЛИ** |
| Этаж | `first_floor_only` (строго первый), `exclude_basement_and_semi_basement` (исключить подвал и цоколь), `any`. Значение `-1/6` не считать первым этажом. Неясное обозначение этажа требует проверки |
| Цена и площадь | Включительные интервалы «от/до», цена в рублях и площадь в м². Разные группы условий объединяются по **И** |
| Районы | Один или несколько районов по **ИЛИ**, проверка по географии объекта, а не по простому упоминанию слова |
| Продавец | `all` или `confirmed_owner_only`. Метка «частное лицо» сама по себе не подтверждает собственность |
| Описание | Обязательные признаки и предпочтения: отдельный вход, витрина, первая линия, мощность, потолки, мокрая точка, ворота и другие свободно заданные критерии |

Проверять признаки в порядке: структурированные поля → детерминированные правила → анализ публичного описания Yandex AI только для неразрешённых случаев. Для каждого критерия сохранять `matched / contradicted / unknown`, источник и подтверждающий фрагмент. Формулировки «можно оборудовать», «планируется» и отрицания не подтверждают наличие признака. Несоответствие обязательному условию переводит объявление в `rejected`, отсутствие сведений — в `needs_review`, все подтверждённые условия — в `confirmed`. Предпочтения влияют только на ранжирование.

В режиме `confirmed_owner_only` выдавать в подтверждённых результатах лишь объекты с зафиксированной проверкой собственника. Неизвестные объявления можно показывать отдельно в `needs_review` без нарушения строгого фильтра. Источник, дата и метод подтверждения должны быть видны сотруднику.

### 3.2. Закладки, подборки и перенос в CRM

Разделить сущности и действия:

1. **Внешнее объявление:** нормализованная запись источника с историей получения, без обязательного создания `Property`.
2. **Закладка риелтора:** личное сохранение объявления с заметкой и статусом «изучить / уточнить / исключить».
3. **Кандидат в подборку (`ClientNeed`):** связь объявления с конкретной потребностью, личными комментариями и состоянием рассмотрения. Кандидат ещё не означает отправку клиенту.
4. **Объект CRM:** по явной команде создать или обновить `Property(sourceType=external_market)` с происхождением объявления.
5. **Факт предложения:** по отдельной команде создать `NeedPropertyMatch`, используя связанный `Property`. После этого применять существующие показы, КП, реакции и историю клиента.

Для промежуточной подборки допустима новая модель `SearchSelection` или эквивалентная связь внешнего объявления с `ClientNeed`. **Не создавать `NeedPropertyMatch` до появления `Property` и фактического предложения.** Один внешний объект может входить в разные подборки. Закладки сами не попадают в общий каталог.

Сохранённый поиск содержит название, город, фильтры, источники и необязательную ссылку на потребность. Запуск вручную. Новизну объявлений и изменение цены определять относительно предыдущего успешного результата. Повторный перенос не должен создавать дубли `Property`. Идентификацию вести по площадке, ID объявления и отдельному ID помещения, а при недостатке ключей требовать ручной проверки.

Из карточки объявления доступны задача «Уточнить», переход в каталог, создание факта предложения, запись показа и добавление в КП. Если внешнего объявления ещё нет в `Property`, перед созданием КП или предложения пользователь подтверждает его перенос в CRM. Права на `ClientNeed` проверять сервером при каждой операции.

Для внешнего объекта хранить **раздельно** данные площадки и результат звонка сотрудника: проверивший, дата, актуальность (`доступен / забронирован / снят / неизвестно`), подтверждение цены и собственника, дата следующей проверки. Отказ источника не означает снятия объекта с рынка.

## 4. Скрапер и резервный веб-поиск (P1-Б)

Подключить серверным адаптером пакет `real-estate-scrapper-2.1.0.tgz`. До разработки проверить фактический README, экспорт `RealEstateScraper.create({ browser: true })`, JSON-формат, Chrome, Node 24 и Docker. Локальный путь `D:\Real-Estate-Scrapper` в продакшене не использовать. Зафиксировать версию пакета и набор тестовых страниц.

Источники: Циан, Мир Квартир, OnRealt, Домклик, Яндекс Недвижимость, Юла, Авито. Для каждого запуска хранить статус источника (`success / partial / blocked / timeout / unsupported_filter / error / disabled`), число результатов и причину неполного покрытия. Отдельный сбой не отменяет успешные результаты. Не автоматизировать обход CAPTCHA или другие запрещённые методы доступа. Условия работы площадок проверять, ручное добавление по ссылке сохранять.

Нормализовать источник, ID объявления/помещения, URL, назначение, операцию, цену и единицу цены, площадь, этаж, адрес/район, продавца, описание, изображения и время проверки. Многопомещенные объявления делить на самостоятельные единицы. Повторно фильтровать на сервере. Точные дубли определять по идентификаторам источника, возможные межплощадочные совпадения показывать на проверку. Внешние URL проверять на SSRF, ограничить тайм-ауты и число параллельных заданий. Сохранённые подборки и закладки доступны при недоступности площадки.

**Алгоритм выбора источника:**

- **Основной:** скрапер всех включённых и поддерживающих запрос площадок. Успешный ответ с нулём совпадений означает корректный пустой результат.
- **Частичный отказ:** показать успешные результаты и статусы отказавших площадок. Дополнительный веб-поиск запускает пользователь при разрешении руководителя.
- **Полный технический отказ:** все применимые включённые адаптеры завершились ошибкой/блокировкой/тайм-аутом либо не поддерживают обязательный фильтр, и ни один не вернул успешный набор данных. Автоматический `web_search` разрешён **только** при включённом ИИ, отдельном разрешении автоперехода и доступном бюджете.
- **Нет включённых площадок или нет совпадений при исправных источниках:** автоматически веб-поиск не запускать. Доступен ручной запуск, если руководитель его разрешил.
- **Веб-поиск отключён или лимит исчерпан:** показать объяснение и ручные фильтры без повторяющихся платных попыток.

Веб-поиск выполняет **отдельный** вызов Yandex Responses API с `tools: [{ type: "web_search", ... }]`. Передавать только условия поиска без ФИО, контактов и внутренних заметок клиента. Из текстов объявлений, отправляемых модели для анализа, удалять телефоны и электронные адреса, если они не требуются для проверки признака. Сохранять исходные URL и происхождение `sourceMethod=web_search`. Любой результат веб-поиска проходит ту же серверную проверку. Недостаток фактов ведёт к `needs_review`. Объявление без проверяемого первоисточника нельзя автоматически считать подтверждённым или предлагать клиенту.

## 5. Yandex AI: настройки и расходы (P1-Б)

Использовать OpenAI-совместимый Responses API `https://ai.api.cloud.yandex.net/v1` на **сервере** с `api_key`, `project=folder`, моделью `gpt://{folder}/{model}` и `store=false`. Начальная модель — `aliceai-llm-flash/latest`. Совместимость выбранной модели и веб-инструмента проверить реальным ограниченным запросом. Для извлечения фильтров использовать отдельный вызов без инструментов, результат проверять Zod. Содержимое объявлений считать недоверенным, модель не должна получать доступ к закрытым клиентским данным или операциям изменения CRM.

Экран руководителя `/settings/ai`: включение ИИ, скрапера, браузерного режима и отдельных площадок, разрешение ручного `web_search`, отдельный переключатель автоматического резервного поиска, модель, размер поискового контекста, лимиты на пользователя/задание/день и **общий месячный бюджет**. Сотруднику показывать разрешённые режимы и остаток лимита. Настройки сохранять серверно. Пределы из ENV имеют приоритет над UI.

Записывать тип AI-вызова (`parse`, `description`, `web_search`), пользователя и задачу, модель, входные/выходные токены, фактические вызовы поиска, оценочную и известную фактическую стоимость, результат, время. Тарифы хранить в настраиваемой таблице с датой действия. При параллельных запусках резервировать бюджет атомарно до запроса и сверять с фактическим расходом после завершения. При отсутствии данных о расходе использовать консервативную оценку. Просмотр затрат доступен руководителю. Секреты не отправлять браузеру и не записывать в логи.

**Конфигурация:** дополнить `.env.example` и серверную валидацию. Ключ заполняет владелец установки. Значения по умолчанию безопасны для запуска без платных сервисов.

Проверить даты задач, границы отчётных суток, календарь, повторения и уведомления. Существующие UTC-времена в БД сохранить. Для сотрудников в других часовых поясах допускается индивидуальная настройка отображения без изменения часового пояса всей базы.

## 6. Галерея и документы объекта (P1-А)

На `/properties/new` и `/properties/{id}/edit` добавить множественный выбор фотографий и документов, предпросмотр, очередь, удаление до отправки, результат по каждому файлу и повтор неудачной загрузки. Вначале создать `Property`, затем загрузить файлы по его ID. При отказе загрузки не создавать повторно объект и не оставлять файл без связи. Сохранить существующие форматы и лимиты.

В карточке объекта: обложка, вкладки «Фотографии» и «Документы», галерея миниатюр, увеличение и клавиатурная навигация, подписи, сортировка, главное фото, архивирование. Главное фото показывать в каталоге. Расширить текущие связи `DocumentProperty` метаданными `sortOrder`, `isCover`, `caption` либо эквивалентной нормализованной моделью. На объект допускается одно активное главное фото. Существующие документы типа `photo` должны корректно перейти в галерею.

Формировать миниатюры, ограничивать размер изображения при декодировании, удалять геометки EXIF. Выдавать файлы только через серверную проверку прав. Фото объекта общего каталога и закрытые договоры имеют разные политики доступа, в том числе для сканов JPG/PNG. Файлы хранить вне `public/` и включать в backup/restore.

Фотографии внешних площадок показывать или включать в КП только при допустимом использовании. Сохранять первоисточник, избегать автоматического копирования чужих материалов без основания.

## 7. КП, выгрузки и чек-листы (P1-А)

Риелтор выбирает объекты каталога или подборки клиента и формирует КП с фотографиями, характеристиками, ценой, примечаниями и ссылками. Нужны предпросмотр, изменение порядка, исключение позиций и новая редакция из предыдущего КП. Использовать существующий `CommercialOffer` и снимок значений на момент формирования. Изменение рыночной цены не влияет на уже сформированное предложение. Статус «отправлено» назначать только по действию пользователя.

До получения фирменных образцов реализовать **нейтральные выгрузки** на данных CRM:

| Материал | Формат |
|---|---|
| КП / подборка недвижимости | DOCX и печатный HTML, PDF после проверки локальной конвертации |
| Карточка объекта для внутренней работы | DOCX или печатный HTML |
| Объекты и результаты поиска | CSV для Excel с UTF-8 BOM, фильтрами и источниками |
| Реестры сделок, комиссий и задач | Существующий CSV/Excel с нужными фильтрами и RBAC |
| Чек-лист документов сделки | HTML/DOCX, статус каждого пункта и приложенный файл |

Сохранить существующие экспорты. Включать только реально известные сведения и разрешённые изображения, исключить выдуманные условия и реквизиты. Для шапки использовать настраиваемые логотип и реквизиты юридического лица из CRM.

Чек-лист сделки строить по её типу: правоустанавливающие и технические материалы, выписка ЕГРН, обременения, полномочия подписанта, сведения юрлица/ИП, договор, акт, счёт. Для пункта поддержать `нет / на проверке / проверено / не требуется`, ответственного, дату и ссылку на файл. Пользователь определяет применимость и достаточность документов. В P2 после получения утверждённых шаблонов добавить версионируемые DOCX-формы с заполнением полей и предпросмотром. Пока готовых шаблонов нет, договоры допускается загружать вручную.

## 8. Календарь, ежедневник и внутренние уведомления (P1-А)

Календарь `/calendar` показывает **существующие** задачи по `Task.dueAt`, показы по `Showing.scheduledAt`, контрольные даты договоров и отдельные встречи. Режимы день/неделя/месяц/повестка, фильтры по сотруднику, типу, статусу. Быстрое создание и перенос проходят через действующие сервисы с сохранением инвариантов и проверкой прав. Один показ не должен порождать вторую независимую запись для календаря.

Для встреч и личной занятости добавить минимальный `CalendarEvent`: начало, конец, весь день, заголовок, описание, ответственный, видимость, повторение и опциональные ссылки на CRM. Отличать временной интервал встречи от срока задачи. Поддержать перенос, предупреждение о пересечении и отображение в установленном часовом поясе. Личные события скрывают название и описание от других сотрудников, руководитель при необходимости видит только факт занятости.

На `/today` объединить повестку, просроченные задачи, ближайшие показы и личные записи. Свободные интервалы вычислять лишь по событиям с известным началом и окончанием. Срок `Task.dueAt` не считать продолжительностью занятости, а показ без длительности отображать как точечное событие. Дать быстрые действия выполнения/переноса. Состояние синхронно с `Task`, `Showing` и `CalendarEvent`.

Уведомления **исключительно внутри CRM**: колокольчик, счётчик непрочитанных, `/notifications`, переход к событию, отметка прочтения и «Напомнить позже». Источники: задача, назначение, показ, срок договора, возврат из паузы, ежегодный и постсделочный контакт. Напоминания в момент события или заранее за 15 минут, час, день либо интервал пользователя. Отложенное уведомление не меняет срок задачи. При переносе исходного события будущие уведомления актуализировать.

`Notification` хранит получателя, вид события, ID источника, время, состояние, `readAt`, `snoozedUntil` и ключ дедупликации. Фоновый исполнитель в Docker должен работать без открытого браузера, восстанавливать пропущенные задания после перезапуска и исключать дубли. В active/standby-режиме уведомления создаёт только активный экземпляр. Сведения о чужом клиенте не включать в текст или API уведомления. Email, push, SMS и MAX-бот входят в P3.

## 9. Дизайн и удобство (P1-А)

Сохранить Tailwind CSS 4 и работоспособные компоненты. Ввести единые визуальные токены, отступы, размеры, состояния элементов. При необходимости подключить `shadcn/ui`, а для календаря — бесплатные компоненты `FullCalendar Standard`, после проверки совместимости. Массовая перепись интерфейса не требуется.

Обновить прежде всего «Сегодня», карточки клиента/потребности, поиск, подборку, каталог, галерею, КП и календарь. Добавить сворачиваемую навигацию, удобные фильтры, быстрые действия, понятные ошибки, адаптивность от 360 px, клавиатурную навигацию и видимый фокус. Не усложнять рутинные операции декоративными элементами. Проверить ключевые сценарии у сотрудников агентства.

## 10. Доступ, отчёты и инварианты

### 10.1. Безопасность (P0)

Исправить выдачу персональных данных через вложенные DTO при `clientVisible=false`. Проверенные места: `getDeal`, `getNeedCard`, `listNeeds`, `getAgreement`, `listAgreements`, `listRequests`, `getRequestCard`. Проверить связанные данные `parties`, `commissions`, `payer`, `client`, `contacts`, а также поиск, экспорт, новые подборки, уведомления, AI-сервисы и загрузку файлов.

**Сервер возвращает только разрешённые поля.** Скрытие в интерфейсе не защищает JSON. Сохранить правила: риелтор видит своих клиентов, каталог объектов общий, контакты собственников доступны по ответственному и индивидуальному `grant`. Доступ к объекту или сделке сам по себе не даёт прав на чужую клиентскую карточку. Защищённый документ не становится общедоступным через дополнительную ссылку на публичный объект. Проверять доступ при каждом скачивании, учитывать отзыв прав. Тестировать прямые запросы к ID, чужие вложенные записи, экспорт, файлы и поиск.

Для скрапера, изображений и внешних URL применять защиту от SSRF и опасных файлов, исключать выполнение недоверенного HTML и инструкций из описаний. Секреты хранить только на сервере. Все команды изменения данных должны проходить валидацию и RBAC. Вести аудит существенных операций.

### 10.2. Отчёты и правила данных (P1-А)

Для KPI и воронки добавить переходы к исходным записям: обращения, потребности, показы, КП, сделки, причины закрытия, повторные активации, комиссии. Фильтры и временные границы у агрегата и детального списка совпадают. Завершённые сделки считать по дате закрытия, отправленные КП — по дате отправки. Если показатель считает уникальные потребности, детализация также должна показывать уникальные потребности. Добавить метрики контроля перспективных обращений и своевременности контактов.

Для `ClientNeed.status=paused` требовать специальную открытую задачу возврата с ответственным и сроком. Обычная задача не удовлетворяет правилу. Завершение/отмена последней задачи возврата допустимы только с новой задачей возврата или изменением статуса потребности в одной транзакции. Проверить перенос и повторение задачи.

## 11. Проверки, документация и материалы ВКР

**Автотесты:** unit для фильтров, этажей, собственника, анализа описаний, бюджета ИИ, дедупликации и правил уведомлений. Integration на PostgreSQL для связей кандидата с потребностью, переноса в `Property`, `NeedPropertyMatch`, КП, документов, задач, календаря, отчётов, DTO и импорта. Authorization-тесты на все способы раскрытия чужих данных. E2E Playwright для маршрута «обращение → поиск → подборка → КП → показ → сделка → повторный контакт».

Скрапер тестировать на сохранённых страницах **семи** площадок, включая отказ, `429`, нулевой корректный результат и ошибку `-1/6`. Web-search тестировать через моки контрактов, проверяя ручной запуск, автопереход, лимиты и отсутствие двойной оплаты. Настоящий ограниченный smoke-тест Yandex AI проводить отдельно с секретами. Не считать моки подтверждением доступности внешних площадок.

**Эксплуатация:** typecheck, lint, Vitest, Playwright, Docker build, чистая установка, миграция рабочей схемы, backup/restore с файлами, восстановление очереди уведомлений после перезапуска, три одновременных пользователя. Измерить NFR-14 на согласованном оборудовании. Сохранять логи CI, результаты запусков и SHA проверенного коммита. Повторить применимые сценарии основного ТЗ, включая T01–T10, и отдельные проверки portable/off-site по мере доступности среды.

**Импорт Excel:** пока у заказчика нет реального образца, проверить текущий синтетический файл, настраиваемое сопоставление колонок, dry-run, дубли и отчёт по строкам. После получения обезличенного рабочего Excel обязательно проверить реальные секции и поля, количество строк и повторный импорт без потерь. До такой проверки у реальной миграции статус `PARTIAL`. Структуру отсутствующего файла не предполагать.

**Для защиты ВКР:** подготовить архитектуру, ER-диаграмму, AS-IS/TO-BE, трассировку требований, демонстрационную инструкцию, протокол испытаний и оценку затрат. Сравнить время регистрации обращения, поиска и подготовки КП на воспроизводимых сценариях. При расчёте экономического эффекта учитывать эксплуатацию скрапера, AI-токены, веб-поиск, хостинг и время сотрудников. Разделять измеренные и прогнозные результаты.

С помощью Playwright сделать **подлинные скриншоты** рабочих экранов на обезличенных данных в `docs/vkr/screenshots/`: «Сегодня», клиент, потребность, поиск и корректировка фильтров, состояние отказа площадки, веб-резерв, подборки, объект с галереей, КП, календарь, уведомления, сделка/документы и отчёт. Для каждого сохранить описание сценария, дату, версию приложения и тестовые данные. Изображения макетов не выдавать за реализованный функционал. В тексте ВКР выбрать значимые экраны, остальные поместить в приложение.

**Обновить документацию:** `README.md`, `.env.example`, `IMPLEMENTATION_REPORT.md`, `docs/requirements-traceability.md`, `docs/security-review.md`, пользовательские инструкции, API, модель данных, эксплуатацию/резервные копии, параметры ИИ, статусы источников, журнал решений и сценарии приёмки. Все статусы `PASS / PARTIAL / BLOCKED` подтверждать фактическими проверками.
