# Планер v3.1 — PL-01…PL-05, AT-11 / AT-12

## Реализация

- `/today` и `/tasks` открывают единый `/calendar`: день, неделя, месяц, три месяца, мини-календарь; мои / все доступные / сотрудник; клиент выбирается по имени. Фильтры типа, приоритета, статуса и срока проверяются сервером.
- Task, Showing, CalendarEvent и начало/окончание Agreement — вычисляемое представление первичных записей. Задачи postdeal входят как Task; служебная задача показа исключается, сам показ остаётся один. Личные встречи других сотрудников проецируются в «Занято», без sourceId, текста и ссылок CRM. Фильтр клиента не раскрывает участников личной встречи.
- Цвет определяется `plannerTone`: терминальные статусы серые, просрочка/critical красные, близкий срок жёлтый, остальные зелёные. Высокий деловой приоритет сам по себе не означает просрочку. Порог по умолчанию 24 ч, меняется руководителем с optimistic concurrency и аудитом.
- Три месяца используют `/calendar/aggregate`: PostgreSQL GROUP BY по локальному дню и цвету, без чтения Task/Showing/Agreement строк в Node и без передачи их браузеру. Повторяющиеся определения встреч раскрываются на сервере отдельно; максимум 1000 определений с явной ошибкой превышения. По клику загружается только выбранный день. Для обычного подробного списка лимит 1000 строк каждого вида: требуется сузить фильтр при превышении.
- Чек-лист TaskChecklistItem: порядок, ответственный, срок, обязательность, `open/done/cancelled`, результат, автор/момент выполнения. Все операции проверяют доступ к родительской задаче и её бизнес-контексту. Изменение пункта требует его expectedUpdatedAt. Блокировка родителя сериализует изменения пунктов и завершение; открытые обязательные пункты требуют явного подтверждения `confirmOpenRequired`, обход записывается в AuditLog. Повтор копирует структуру чек-листа с новыми открытыми пунктами.
- Повторы Task используют прежние kind/interval/until либо RRULE. Квартал — monthly/3, будни — WEEKLY/BYDAY, календарные серии поддерживают YEARLY и MONTHLY/INTERVAL=3, UNTIL/COUNT. parentTaskId остаётся ссылкой экземпляра на корень серии. Следующий экземпляр появляется при выполнении текущего, по прежнему контракту Task.
- Шаблоны новой задачи: «Проверить декларацию», «Индексация аренды», «Контроль договора», «Повторный контакт». Массовые задачи по 1–100 доступным клиентам: предпросмотр, подтверждение, BulkTaskBatch. Одинаковый ключ и payload возвращают прежнюю пачку, другой payload даёт конфликт. Конкурентные повторы сериализованы advisory lock и UNIQUE idempotencyKey.
- Существующий worker создаёт независимые фазы до срока, в срок, просрочка (через минуту), assignment и дополнительные reminderOffsets. Старые kind сохраняются, фаза входит в dedupKey. Рестарт/конкурирующий tick не дублирует запись; snooze не меняет срок источника. При переносе/закрытии pending уведомления снимаются. DTO уведомления содержит понятный текст фазы.
- В открытой вкладке доступны включение звука и разрешение системных уведомлений. Проверка доставки размещена рядом с колокольчиком оболочки; разрешение запрашивается только по кнопке пользователя. В localStorage сохраняются только настройки и идентификаторы доставки; бизнес-текст не сохраняется. Внешнего push нет. Сам звук зависит от разрешённого браузером AudioContext после пользовательского действия.

## API

| Маршрут | Контракт |
|---|---|
| GET `/api/v1/calendar` | from/to ISO с зоной, employee?, clientId?, type?, priority?, status?, deadline=overdue/soon/controlled/closed; items с tone/priority |
| GET `/api/v1/calendar/aggregate` | те же фильтры; days=[day,total,red,yellow,green,gray], total, soonThresholdHours; без первичных строк |
| GET/PUT `/api/v1/calendar/settings` | GET порог и updatedAt/null; PUT manager: soonThresholdHours 1–8760, expectedUpdatedAt/null |
| GET/POST `/api/v1/tasks/{id}/checklist` | GET items/прогресс/просрочки; POST title, sortOrder, responsibleUserId?, dueAt?, required, status, result? |
| PATCH `/api/v1/tasks/{id}/checklist/{itemId}` | Полная форма пункта и expectedUpdatedAt; чужой itemId/родитель → 404 |
| POST `/api/v1/tasks/{id}/complete` | Прежний контракт + confirmOpenRequired; без подтверждения → 422 OPEN_REQUIRED_CHECKLIST |
| POST `/api/v1/tasks/bulk` | clientIds, task, idempotencyKey UUID; preview → previewToken; commit дополнительно confirmed=true и previewToken; возвращает batchId/count/repeated |

Индексы используются из существующей v3.1 миграции: Task(responsible,status,due), Task(status,due), TaskChecklistItem(task,sortOrder)/(responsible,status,due), BulkTaskBatch UNIQUE idempotencyKey, индексы связей, CalendarEvent(owner,start)/(start), Agreement(status,validUntil). Схема и миграции этим агентом не менялись, зависимости не добавлялись.

## Приёмка и воспроизведение

Preconditions: миграции v3.1, синтетическая crm_test_f; для браузера — crm_demo и SEED_* из .env. Тесты не используют реальные ПДн/AI/площадки.

- `tests/unit/planner-v31.test.ts`: точные границы цветов/порогов, терминальные статусы, суммы дневных агрегатов, квартал/год/високосный день/окончание серии и roundtrip формы.
- `tests/integration/planner-v31.test.ts`: обязательные пункты/подтверждение/версии, аудит, идемпотентность и конкурентный retry пачки, повтор с чек-листом/COUNT, совпадение агрегатов с RBAC-проекциями, настройка manager, restart/snooze всех фаз. Дополнительно 1500 Task → один дневной агрегат и ноль вызовов task.findMany.
- `tests/authorization/planner-v31.test.ts`: прямые API чужих задач/пунктов, подстановка itemId другого родителя, чужие клиенты в пачке и фильтре агрегатов.
- Регрессия: calendar-ux, calendar-notifications, notification-worker, task-rules; всего **65/65 PASS** в 10 файлах, PostgreSQL с чистой миграцией crm_test_f.
- `node tests/e2e/planner-v31-smoke.mjs`: настоящий Chromium, DEMO. Проверяет четыре режима, фактические CSS-цвета, вход с Сегодня, мини-календарь, отсутствие запроса строк в трёхмесячном режиме, ленивый день, чек-лист и подтверждение, массовый предпросмотр и commit. Синтетические задачи скрипта удаляются после проверки. Скриншоты пишутся только в `D:/crm-review/planner-v31`, вне Git.
- `npx tsc --noEmit` — PASS на заключительном прогоне; ESLint изменённых TS/TSX/тестов с `--max-warnings=0` — PASS. Ранее общий tsc временно падал в незавершённых чужих зонах; файлы поиска/подборок не исправлялись этим агентом.

AT-11: браузерная DEMO-проверка четырёх режимов/цветов плюс PostgreSQL RBAC/aggregate parity.
